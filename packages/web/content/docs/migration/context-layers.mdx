# Memory Layers → Context Layers

Noetic's layer system was named after one thing a few layers happened to do
(store memories) rather than what all of them are for: **assembling the model's
context window** on every turn — recall, budget allocation, history projection,
the item-append pipeline, steering.

So `MemoryLayer` is now `ContextLayer`, and `@noetic-tools/memory` is now
[`@noetic-tools/context`](https://www.npmjs.com/package/@noetic-tools/context).

<Callout type="info">
  **This is a minor release, not a breaking one.** Every pre-rename name still
  resolves through a `@deprecated` alias, and every pre-rename config key is
  still accepted. You can upgrade without touching your code, then rename at
  your own pace.

  The one genuine behaviour change is the two renamed layer IDs — see
  [What actually breaks](#what-actually-breaks).
</Callout>

## Package

```diff
- import { workingMemory } from '@noetic-tools/memory';
+ import { workingMemoryContext } from '@noetic-tools/context';
```

`@noetic-tools/memory` is still published and now re-exports
`@noetic-tools/context` wholesale, so the old specifier keeps working. It
receives no further changes.

Most applications import from `@noetic-tools/core`, which re-exports the whole
surface — those are unaffected by the package rename.

## Types

| Before | After |
|---|---|
| `MemoryLayer<TState>` | `ContextLayer<TState>` |
| `MemoryHooks<TState>` | `ContextLayerHooks<TState>` |
| `MemoryConfig<TLayers>` | `ContextConfig<TLayers>` |
| `ContextMemory` | `ContextData` |
| `InferMemory<T>` | `InferContext<T>` |
| `InferMemoryShape<T>` | `InferContextShape<T>` |
| `MemoryScope` | `ContextScope` |
| `MemoryCallModelRequest` | `LayerCallModelRequest` |
| `MemoryTraceSpan` | `LayerTraceSpan` |
| `ToolMemory` | `ToolContext` |
| `ToolMemoryDeclaration` | `ToolContextDeclaration` |
| `WorkingMemoryConfig` / `WorkingMemoryState` | `WorkingMemoryContextConfig` / `WorkingMemoryContextState` |
| `ObservationalMemoryConfig` | `ObservationalContextConfig` |
| `TemporalMemoryConfig` | `TemporalContextConfig` |
| `PlanMemoryConfig` | `PlanContextConfig` |

The generic parameter `TMemory` is now `TContext` — `Step<TContext, I, O>`.
That is a positional parameter, so it only matters if you named it explicitly.

Unchanged: `BudgetConfig`, `LayerTimeouts`, `LayerDataDecl`, `LayerFunctionDecl`,
`LayerProvides`, `LayerHandle`, `Slot`, `StorageAdapter`, `ScopedStorage`, every
hook param/result type, `RerenderScope`, `ProjectionPolicy`.

## Builders

| Before | After |
|---|---|
| `memory([...])` | `context([...])` |
| `workingMemory()` | `workingMemoryContext()` |
| `observationalMemory()` | `observationalContext()` |
| `temporalMemory()` | `temporalContext()` |
| `planMemory()` | `planContext()` |
| `toolMemoryLayer()` | `toolContextLayer()` |

`historyWindow`, `steering`, `fileReference`, `staticContent`, and
`durableTaskState` are unchanged.

`workingMemory` keeps "memory" in its new name on purpose: *working memory* is a
term of art, and the layer really is a small mutable scratchpad the model reads
and writes. The others were named after the system, not the concept.

## The `memory:` config key

Renamed to `context:` on `provide`, `spawn`, `tool`, `react`, the `AgentHarness`
constructor, `createContext`, `execute`, and `restore`.

```diff
  step.provide({
    id: 'with-layers',
    child: agent,
-   memory: [workingMemory()],
+   context: [workingMemoryContext()],
  })
```

Both keys are accepted. If you pass both, `context` wins.

The JSON workflow format is **unchanged** — `provide` and `spawn` nodes already
used a `layers` array, and still do:

```json
{ "kind": "provide", "layers": ["todo"], "child": { "...": "..." } }
```

## `ctx.memory` → `ctx.context`

```diff
- const todos = ctx.memory['todo'].items;
+ const todos = ctx.context['todo'].items;
```

Same inside a tool: `toolCtx.memory` → `toolCtx.context`. Both old accessors
still return the identical object.

## What actually breaks

Two built-in layers changed their `id`, and layer IDs are not just internal:

| Layer | Old id | New id |
|---|---|---|
| `workingMemoryContext()` | `working-memory` | `working-context` |
| `observationalContext()` | `observational-memory` | `observational-context` |

That id is used in four places, so changing it has real consequences:

1. **The tool name the model sees.** `working-memory/update` is now
   `working-context/update`. This invalidates prompt caches and will break any
   eval fixture or transcript assertion that matches on the old tool name.
2. **Persisted layer state.** Scoped storage keys are
   `layers/{layerId}/{scopeKey}/`, so previously stored `working-memory` and
   `observational-memory` state is **not** migrated and will not be read back.
   Affected agents start those two layers from their initial state.
3. **Checkpoint restore.** Snapshots are keyed by layer id, so restoring a
   checkpoint written before the upgrade will not repopulate these two layers.
4. **Workflow JSON** that names them in `provide.layers[]` / `spawn.layers[]`
   must be updated to the new strings.

Every other built-in layer id (`temporal`, `plan`, `steering`, `history-window`,
`file-reference`, `durable-task-state`) is unchanged, as are the `ContextScope`
values (`'thread' | 'resource' | 'global' | 'execution'`) and `Slot.WORKING_MEMORY`.

If preserving that state matters to you, pin the previous major before
upgrading, or set the ids explicitly on your own layer instances.
