## Step Union

The `Step` type is a discriminated union over the `kind` field:

```ts
import type {
  Step,
  StepConditional,
  StepDecide,
  StepInParallel,
  StepCallModel,
  StepLoop,
  StepWithContext,
  StepRunCode,
  StepSpawn,
  StepInvokeTool,
} from '@noetic-tools/core';

type _AssertShape<TContext, I, O> =
  | StepRunCode<TContext, I, O>
  | StepCallModel<TContext, I, O>
  | StepInvokeTool<TContext, I, O>
  | StepDecide<TContext, I, O>
  | StepConditional<TContext, I, O>
  | StepInParallel<TContext, I, O>
  | StepSpawn<TContext, I, O>
  | StepWithContext<TContext, I, O>
  | StepLoop<TContext, I, O>;

type _AssertSubset<TContext, I, O> = _AssertShape<TContext, I, O> extends Step<TContext, I, O>
  ? true
  : false;
```

The exported `Step` union additionally includes [`StepSchedule`](#stepschedule) for fixed-interval scheduling and [`StepSequence`](#stepsequence), what an array of steps becomes.

### StepReplay

Every step interface extends `StepReplay<TContext, I>`, so these fields apply to every row below. See [Replay Identity](/docs/framework/durability#replay-identity).

| Field | Type | Required | Description |
|---|---|---|---|
| `durable` | `boolean` | no | Defaults to `true`. `false` keeps the step out of the step ledger: never replayed or recorded on resume. |
| `replayKey` | `(input: I, ctx: Context<TContext>) => string` | no | Content key the ledger uses instead of the execution path. |

### StepEmitItems

Every step interface also extends `StepEmitItems<TContext, I, O, M>`. See [Emitting Items Early](/docs/framework/steps#emitting-items-early) and [Custom Items](/docs/framework/custom-items).

| Field | Type | Required | Description |
|---|---|---|---|
| `emitItems` | `StepEmitItemsOption<TContext, I, O, M>` | no | What to add to the conversation as the step runs. Items are appended to the item log and streamed as `item_appended`; a custom item's events stream as `custom_item_event`. A step that throws emits nothing. A replay streams them again only under the harness's `emitItemsOnReplay`. |
| `customItems` | `M extends CustomItemMap` | no | Custom items only this step may emit, by name. |

| Type | Definition |
|---|---|
| `StepEmitItemsOption<TContext, I, O, M>` | `boolean \| StepEmitItemsFn<TContext, O> \| StepEmitItemsConfig<TContext, I, O, M>`. `true` emits the output as a final item. |
| `StepEmitItemsFn<TContext, O>` | `(output: O, ctx: Context<TContext>) => StepEmitItemsResult \| Promise<StepEmitItemsResult>` |
| `StepEmitItemsResult` | `string \| Item \| ReadonlyArray<Item> \| undefined`. A string becomes an assistant message; items are appended as given and must pass the context's item schemas; `undefined` or `''` emits nothing. |
| `StepEmitItemsConfig<TContext, I, O, M>` | `{ item: N; onStart?: EmitHook; onDone?: EmitHook }` for each item name `N` in `M`, with hooks typed by that item, or `{ onStart?, onDone? }` without an item, giving text or standard items. |
| `EmitHook<TContext, V, E, F>` | `(value: V, ctx) => F \| undefined \| Promise<…> \| Generator<E, F \| undefined> \| AsyncGenerator<E, F \| undefined>`: yields are events `E`, the return value the final fields `F`. |

## StepDecide

`StepDecide<TContext, I, O>`

A step that asks a model typed questions and returns typed answers with probabilities. It reads the conversation but never appends to it, and runs no steering hooks. Built by [`decide()`](/docs/framework/steps/decide).

| Field | Type | Required | Description |
|---|---|---|---|
| `kind` | `'decide'` | yes | Discriminant |
| `id` | `string` | yes | Step identifier |
| `model` | `Lazy<string, TContext>` | no | Decision model id. Falls back to `harness.config.decisionModel` |
| `instructions` | `Lazy<string \| undefined, TContext>` | no | Shared framing for every question |
| `questions` | `DecideQuestions` | yes | Question map keyed by question id |
| `view` | `'full' \| 'layers' \| 'none'` | yes | How much of the assembled view the model sees. `decide()` defaults it to `'full'` |
| `context` | `(ctx: Context<TContext>) => Record<string, unknown> \| Promise<Record<string, unknown>>` | no | Typed state read from context layers, sent as one JSON entry named `context` |
| `projection` | `ProjectionPolicy` | no | Budget for the decision's view. Defaults to `DECISION_PROJECTION` |
| `samples` | `number` | yes | Runs averaged on the estimated path. `decide()` defaults it to `1` |
| `emit` | `boolean \| ((eventType, data) => boolean)` | no | Controls framework event emission for this step |
| `_answers` | `O` | no | Phantom field carrying the answers type for inference. Never set at runtime |

### DecideStep

```ts validate=none
type DecideStep<TContext, I, Q extends DecideQuestions> =
  StepDecide<TContext, I, DecideAnswers<Q>> & { readonly questions: Q };
```

What `decide()` returns: a `StepDecide` that keeps its literal question map, so [`routeSwitch`](/docs/framework/operators/route-switch) can infer the questions, choices, and levels it routes by. `DecideAnswers<Q>` maps each question id to its answer type or `Refusal`; `AnsweredAll<Q>` is the same with `Refusal` removed.

`decide()` infers `Q` from `questions`; pass it no type arguments. To type `ctx.context` in the `context` selector, annotate its parameter (`(ctx: Context<MyContext>) => …`).

### Questions and answers

```ts validate=none
type DecideQuestions = Readonly<Record<string, DecideQuestion>>;
type DecideQuestion = BooleanQuestion | ChoiceQuestion | ScoreQuestion;

interface BooleanQuestion {
  type: 'boolean';
  instructions?: string;
  criteria?: { true?: string; false?: string };
  threshold?: number;
}

interface ChoiceQuestion<K extends string = string> {
  type: 'choice';
  instructions?: string;
  choices: readonly K[] | Readonly<Record<K, string>>;
}

interface ScoreQuestion<L extends string = string> {
  type: 'score';
  instructions?: string;
  levels: readonly L[] | ReadonlyArray<{ label: L; description?: string }>;
}

type DecideAnswer = BooleanAnswer | ChoiceAnswer | ScoreAnswer | Refusal;

interface BooleanAnswer {
  type: 'boolean';
  value: boolean;
  probability: number;
}

interface ChoiceAnswer<K extends string = string> {
  type: 'choice';
  value: K;
  confidence: number;
  probabilities: Readonly<Record<K, number>>;
}

interface ScoreAnswer<L extends string = string> {
  type: 'score';
  value: number;
  level: L;
  confidence: number;
  probabilities: Readonly<Record<L, number>>;
}

interface Refusal {
  type: 'refusal';
}
```

See [decide](/docs/framework/steps/decide#answers) for what each field means.

## StepSequence

`StepSequence<TContext, I, O>`

What an array of steps becomes. An array of steps runs in sequence, each step's output the next one's input, everywhere a step goes: `harness.run`, `agentGraph`, `spawn` and `withContext` children, `schedule` bodies, `inParallel` paths, a `conditional` route's pick, `around` and `act`. There is no `step.sequence`; write the array.

| Field | Type | Required | Description |
|---|---|---|---|
| `kind` | `'sequence'` | yes | Discriminant |
| `id` | `string` | yes | The children's ids joined with ` > ` |
| `steps` | `ReadonlyArray<Step<TContext, I, O>>` | yes | The steps, in order; at least two |

An empty array throws [`EMPTY_STEP_ARRAY`](/docs/framework/errors#empty_step_array); a one-element array is its element.

### StepArray, StepArrayInput and StepArrayOutput

```ts
import { AgentHarness, runCode } from '@noetic-tools/core';

const trim = runCode({ id: 'trim', execute: async (input: string) => input.trim() });
const count = runCode({ id: 'count', execute: async (input: string) => input.length });

const harness = new AgentHarness({ name: 'arrays', params: {} });
const length: number = await harness.run([trim, count], '  hi  ', harness.createContext());
```

`StepArray` is a non-empty tuple of steps of any types (`StepLike`). `run` infers the array's input from its first step (`StepArrayInput<T>`) and its output from its last (`StepArrayOutput<T>`). `Steps<TContext, I, O>` is a step or a `StepArray`: what the builders accept.

## StepSchedule

`StepSchedule<TContext, I, O>`

A step that runs a body step on a fixed-interval schedule, optionally woken sooner by a wake channel. Runs forever until the executing context is cancelled. The operator output is `void` — `schedule` does not accumulate iteration outputs.

| Field | Type | Required | Description |
|---|---|---|---|
| `kind` | `'schedule'` | yes | Discriminant |
| `id` | `string` | yes | Step identifier |
| `step` | `Step<TContext, I, O>` | yes | Body step executed on each iteration |
| `interval` | `number` | yes | Park duration between iterations in milliseconds. Must be `>= 0`. |
| `inbox` | `Channel<unknown>` | no | Channel that wakes the parking interval when any value arrives |
| `onError` | `'continue' \| 'fail'` | no | Behavior when `step` throws. Defaults to `'continue'` (record the error and keep parking). |
| `jitter` | `number` | no | Random jitter applied to the park duration in milliseconds. Must be `>= 0`. Defaults to `0`. |

### MergeFn

`MergeFn<TContext, O, R = O>` combines inParallel path results into one output. `R` is the element type of `results`: `O` in `all` mode, `SettleResult<O>` in `settle` mode.

```ts validate=none
type MergeFn<TContext = ContextData, O = unknown, R = O> = (
  results: R[],
  ctx: Context<TContext>,
) => O;
```

### ToolChoice

### Tool

| Field | Type | Description |
|---|---|---|
| `name` | `string` | Tool name (used by the LLM for selection). |
| `description` | `string` | Tool description shown to the LLM. |
| `input` | `StandardSchemaV1<I>` | Schema validating tool input arguments (any Standard Schema v1; Zod is the default). |
| `output` | `StandardSchemaV1<O>` | Schema validating tool return value. |
| `inputJsonSchema` | `Record<string, unknown>` | Explicit JSON Schema override/fallback for non-Zod input. Conversion order is Zod → StandardJSONSchemaV1 → this field; validation-only schemas require it. |
| `event` | `StandardSchemaV1` | Optional schema validating streaming events yielded during execution. |
| `itemSchemas` | `ItemSchemaExtensions` | Optional item schemas for tool-call/result extensions contributed by this tool. `toolResults` schemas are owner-scoped: they validate only this tool's own result items and never reject a sibling tool's results. Schemas are pure shape validators (gates, not normalizers) — the original item is returned on match, and Zod transforms/defaults are unsupported. |
| `decorateResultItem` | `(params) => Item` | Decorate the harness-created tool-result item before it is appended/emitted. The decorated item must satisfy this tool's own `itemSchemas.toolResults` (when declared) — including for error outputs such as malformed-arguments results — or the round fails with `NoeticError` kind `item_schema_mismatch`. |
| `execute` | `(args: InferSchemaOutput<I>, toolCtx: ToolExecutionContext) => Promise<InferSchemaOutput<O>> \| AsyncGenerator<unknown, InferSchemaOutput<O>>` | Async function (or generator) that performs the tool's work. `InferSchemaOutput` is `z.output` for Zod schemas and `StandardSchemaV1.InferOutput` otherwise. |
| `needsApproval` | `boolean` | Optional. Every call needs approval: after the `beforeToolCall` layers allow it, the harness asks its `approveToolCall` approver. A refused call returns an error tool result to the model, or throws `steering_denied` from `invokeTool`. With no approver configured the call runs and the harness warns once per tool name. |
| `context` | `ToolContextDeclaration` | Optional. Declares tool-owned state the runtime materializes into a `ContextLayer`. |

### StepInput and StepOutput

```ts
import { runCode } from '@noetic-tools/core';
import type { StepInput, StepOutput } from '@noetic-tools/core';

const count = runCode({ id: 'count', execute: async (input: string) => input.length });

type CountIn = StepInput<typeof count>;   // string
type CountOut = StepOutput<typeof count>; // number
```

Pull a step's input or output type out of its type. `routeSwitch` uses them to type its output as the union of every case's output.
