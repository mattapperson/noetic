## Quick Example

```ts
import { z } from 'zod';
import { invokeTool, tool } from '@noetic-tools/core';

const calculator = tool({
  name: 'add',
  description: 'Add two numbers',
  input: z.object({
    a: z.number(),
    b: z.number(),
  }),
  output: z.object({
    sum: z.number(),
  }),
  execute: async (args) => ({
    sum: args.a + args.b,
  }),
});

const addStep = invokeTool({
  id: 'add-numbers',
  tool: calculator,
  args: {
    a: 10,
  },
});
```

## What It Does

`invokeTool` invokes a single tool without going through an LLM. This is useful when you know exactly which tool to call -- for example, after a conditional routes to a known action, or as part of a deterministic pipeline.

The optional `args` field lets you preset some or all of the tool's inputs. At runtime, preset args are merged with the step input.

## The Tool Interface

Every tool in Noetic follows the same interface, whether it is passed to `callModel` or invoked directly via `invokeTool`.

| Property | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | `string` | Yes | Tool name (used in LLM function calling) |
| `description` | `string` | Yes | Human-readable description for the model |
| `input` | `StandardSchemaV1<I>` | Yes | Schema defining the tool's input — any [Standard Schema v1](https://standardschema.dev) validator (Zod, Valibot, ArkType, …); Zod is the default |
| `output` | `StandardSchemaV1<O>` | Yes | Schema defining the tool's output |
| `inputJsonSchema` | `Record<string, unknown>` | No | Explicit JSON Schema override/fallback for non-Zod tool input. Zod uses its native converter; other validators can implement StandardJSONSchemaV1. A validation-only schema must provide this field or conversion throws `MISSING_JSON_SCHEMA` |
| `execute` | `(args: I, toolCtx: ToolExecutionContext) => Promise<O>` | Yes | The function that runs the tool. The second argument is a `ToolExecutionContext` — `{ ctx, harness, fs, shell, context, assembledView, lastStepMeta }` — not the step `Context` itself (which is available as `toolCtx.ctx`) |
| `needsApproval` | `boolean` | No | Every call needs the harness approver's go-ahead before it runs — see [Human-in-the-Loop Approval](#human-in-the-loop-approval) |
| `durable` | `boolean` | No | How a call behaves when a run resumes. Unset: recorded, and a call cut off mid-flight runs again with the same `idempotencyKey`. `true`: a call cut off mid-flight is [held](#human-in-the-loop-approval) as `outcome` for a person instead of repeated. `false`: never recorded, always runs again |
| `context` | `ToolContextDeclaration` | No | Declares tool-owned state; the runtime generates a context layer from it |
| `ui` | `ToolUiDeclaration` | No | Render functions (`call` / `progress` / `result` / `error`) so the tool's calls carry their own UI — see [Generative UI](/docs/framework/generative-ui) |

### invokeTool Options

| Property | Type | Required | Description |

| `id` | `string` | Yes | Unique step identifier |

## Defining a Tool

```ts
import { z } from 'zod';

import type { Tool } from '@noetic-tools/core';

const fetchUrl: Tool<typeof UrlInput, typeof UrlOutput> = {
  name: 'fetch-url',
  description: 'Fetch the contents of a URL',
  input: z.object({
    url: z.string().url(),
  }),
  output: z.object({
    body: z.string(),
    status: z.number(),
  }),
  execute: async (args) => {
    const res = await fetch(args.url);
    return {
      body: await res.text(),
      status: res.status,
    };
  },
};

const UrlInput = z.object({
  url: z.string().url(),
});
const UrlOutput = z.object({
  body: z.string(),
  status: z.number(),
});
```

## Standard Schema v1

Tool schemas accept any Standard Schema v1 validator, not just Zod. Runtime validation uses Zod `safeParse` or `~standard.validate` (sync and Promise results are supported), and `execute` receives the parsed/transformed value.

Model-facing JSON Schema uses three tiers: Zod's native converter, the [Standard JSON Schema v1](https://standardschema.dev/json-schema) companion trait, then `inputJsonSchema`. For non-Zod inputs, an explicit `inputJsonSchema` overrides the trait and falls back when the trait converter throws. Zod 4.2+, ArkType 2.1.28+, Zod Mini, VineJS, and Sury implement the trait; Valibot adds it with `toStandardJsonSchema()` from `@valibot/to-json-schema`. Validation-only schemas still require `inputJsonSchema`. Noetic adds no per-validator runtime dependency.

```ts
import { toStandardJsonSchema } from '@valibot/to-json-schema';
import * as v from 'valibot';
import { tool } from '@noetic-tools/core';

const search = tool({
  name: 'search',
  description: 'Search the knowledge base',
  input: toStandardJsonSchema(v.object({ query: v.string() })),
  output: v.object({ results: v.array(v.string()) }),
  execute: async (args) => ({ results: ['Result 1', 'Result 2'] }),
});
```

Standard Schema support covers tool input/output/event schemas and `callModel` / ACP agent structured output only. Channels, context-layer schemas, item extension schemas, and JSON workflow schemas remain Zod-specific.

## Human-in-the-Loop Approval

Set `needsApproval: true` on a tool and give the harness an approver with `approveToolCall`. Before every call to that tool runs, the harness asks the approver, which returns a steering decision: `allow` runs the call; `deny` (or `guide`) refuses it, with `guidance` as the reason. The approver may be async and may wait — for example on a channel a human answers.

```ts
import { z } from 'zod';
import { AgentHarness, channel, tool } from '@noetic-tools/core';

declare const db: { delete(recordId: string): Promise<void> };

const deleteTool = tool({
  name: 'delete-record',
  description: 'Permanently delete a database record',
  input: z.object({
    recordId: z.string(),
  }),
  output: z.object({
    deleted: z.boolean(),
  }),
  needsApproval: true,
  execute: async (args) => {
    // Runs only once the approver allows the call
    await db.delete(args.recordId);
    return {
      deleted: true,
    };
  },
});

// An operator UI reads requests and writes answers.
const approvalRequests = channel('approval-requests', {
  schema: z.object({ toolName: z.string(), toolArgs: z.unknown() }),
  mode: 'queue',
});
const approvalAnswers = channel('approval-answers', {
  schema: z.boolean(),
  mode: 'queue',
});

const harness = new AgentHarness({
  name: 'ops-agent',
  params: {},
  tools: [deleteTool],
  approveToolCall: async ({ toolName, toolArgs, ctx }) => {
    await ctx.harness.send(approvalRequests, { toolName, toolArgs }, ctx);
    const approved = await ctx.harness.recv(approvalAnswers, ctx);
    return approved
      ? { action: 'allow' }
      : { action: 'deny', guidance: 'refused by operator' };
  },
});
```

The approver receives `{ toolName, toolArgs, callId, ctx }`. `toolArgs` are the validated arguments — exactly what `execute` receives — and `callId` is the same id the `tool_call_started` event carries (the model's call id, or the step id for `invokeTool`).

**Order.** Approval is the last gate before `execute`. [`beforeToolCall` gating layers](/docs/framework/context-layers/custom-layers) run first, so a layer refusal stops the call before the approver is asked.

**Refusal.** A refused call never runs. On the model-driven path the model receives an error tool result (`Tool call denied: <guidance>`), the same shape as a gating-layer refusal. An `invokeTool` step throws `NoeticError` kind `steering_denied` carrying the guidance. An approver that throws refuses the call.

**No approver, or `hold`.** A harness without `approveToolCall` does not run the call unapproved: it **holds** it. So does an approver that answers `{ action: 'hold' }`, after sending the request wherever it likes. Nothing is written to the conversation for a held call. The rest of the round's calls run, and the turn waits.

```ts validate=none
const [held] = await harness.pending({ threadId });
// held: { callId, name, args, argsHash, reason: 'approval', dueAt?, … }

await harness.execute(
  { type: 'noetic:decision', callId: held.callId, argsHash: held.argsHash, action: 'allow' },
  { threadId },
);
```

- The answer is a decision item passed to `execute()` on the call's thread. It takes `allow`, `deny` or `guide` (with `guidance`), is never written to the conversation, and starts no turn of its own. The first answer wins; the same answer again is a no-op, and a different one fails with `hold_refused`.
- `argsHash` ties the answer to the exact call the person saw. An answer for other arguments is refused.
- A hold may carry `dueAt`: when it passes the call is denied, or stays held with `onDue: 'keep'`.
- The stream emits `{name}:tool_call_held` with the same fields as `pending()`, and `{name}:tool_call_settled` (`{ callId, name, argsHash, reason, by }`) once the call stops being held. `readHeldCallEvent(event)` reads either, validated.
- On storage with [`park`](/docs/framework/durability#parked-turns) on, a turn whose only work left is a held call parks. Any harness on that storage can list it, answer it and finish the turn, and no finished call runs again.

### Showing a person: `onHeld`

The approver decides what is held; `onHeld` is where a host shows a held call to a person. It is called once per question, with a signal that aborts when the call is settled some other way. Return the answer and the harness takes it as the decision item above, waking the turn if it parked:

```ts validate=none
const harness = new AgentHarness({
  name: 'ops-agent',
  params: {},
  tools: [deleteTool],
  // Answer what needs no one here; hold the rest for a person.
  approveToolCall: ({ toolName }) => (alwaysSafe(toolName) ? { action: 'allow' } : { action: 'hold' }),
  onHeld: async (call, { signal }) => {
    // call.reason: 'approval' (not run yet), 'result' (a tool's hold()), or
    // 'outcome' (a durable tool cut off, effect unknown: allow runs it again).
    const answer = await showCard(call, signal); // close the card when signal aborts
    if (answer === undefined) {
      return undefined; // leave it held; answer later with execute()
    }
    return answer.ok ? { action: 'allow' } : { action: 'deny', guidance: 'The user said no.' };
  },
});
```

- `signal.reason` says how the call was settled: `answer` (a decision, from anywhere), `due` (its deadline), `skipped` (a steer), `cancelled` (the turn was aborted or interrupted, the agent gave up, or the harness closed), or `elsewhere` (another harness over the same storage settled it and finished the turn; seen within two seconds). An answer returned after that is dropped, and nothing throws.
- The harness never waits on the handler: the call waits on its record as it would for any answer. A handler that throws is logged, and the call stays held.
- A handler lives in its process. After a restart, list what is still held with `pending()` and answer it with `execute()`.

A message that arrives while a call is held is a [steer](/docs/framework/runtime#steering-a-running-turn) like any other. Sent with `deliveryMode: 'between-rounds'` or `'next-item'`, it skips the held calls and the turn goes on with it. Set `steerWhileHeld: 'defer'` on the harness to keep the call's question open instead: the steer waits behind the held calls and lands once they are answered. A layer's `onSteer` still has the last word at the `held` steer point. A default (`next-turn`) message waits for the turn to end and does not disturb it.

A tool can also leave its own **result** open, by returning `hold()` once it has done its part:

```ts validate=none
const askPerson = tool({
  name: 'ask_person',
  input: z.object({ question: z.string() }),
  output: z.string(),
  execute: async ({ question }) => {
    await slack.post(channel, question);
    return hold({ request: { question } }); // the body does not run again
  },
});

// Later, when the person replies:
await harness.execute({ type: 'noetic:decision', callId, output: 'Use the new address.' }, { threadId });
```

The `output` is a JSON value, and the decision is the only way to give it: a `function_call_output` item that names a held call is refused with `hold_refused`. A call held by a run you started yourself, such as [`parseAndRunWorkflow`](/docs/framework/json-runtime), has no thread, so add the run's `executionId` to the decision.

A tool marked `durable: true` adds a third kind of hold. If the host dies while it runs, the resumed turn does not run it again: it holds the call with `reason: 'outcome'`. Answer with `{ output }` if it did land, or `{ action: 'allow' }` to run it again.

Traces show the outcome: each `tool.call` span carries `tool.approval` — `approved` or `denied`.

**Self-gating integrations.** A wrapper that gates inside `execute` does not declare `needsApproval`, so its calls are gated once. [`fromAiSdkTool`](/docs/framework/chat-sdk) is one: it waits on its own approval channels and fails the call when it is refused or times out.
