## Quick Example

Define a workflow as a plain JSON document and execute it with `parseAndRunWorkflow`:

```ts
import { parseAndRunWorkflow, AgentHarness, type Tool } from '@noetic-tools/core';

declare const webSearchTool: Tool;

const workflow = {
  version: 1,
  root: {
    kind: 'sequence',
    id: 'research-pipeline',
    steps: [
      {
        kind: 'callModel',
        id: 'gather',
        model: 'openai/gpt-4o',
        instructions: 'Search for recent AI news',
        tools: ['webSearch'],
      },
      {
        kind: 'callModel',
        id: 'summarize',
        instructions: 'Summarize the findings above',
      },
    ],
  },
};

const harness = new AgentHarness({ name: 'runner', params: {} });
const ctx = harness.createContext();
const result = await parseAndRunWorkflow({
  json: workflow,
  harness,
  ctx,
  tools: [webSearchTool],
});
```

The JSON Workflow Runtime lets you express agent workflows as portable JSON documents that are validated, hydrated into live [Steps](/docs/framework/steps), and executed by the [AgentHarness](/docs/framework/runtime). Because the format is pure JSON, workflows can be generated by LLMs at runtime, stored in databases, transferred over the wire, or version-controlled alongside configuration.

Nodes pass text to one another, and [expressions](/docs/framework/expressions) let a workflow read that text as structured data. Written in [JSONata](https://docs.jsonata.org), an expression computes a new value in a `compute` node, picks a `conditional` route with `expr`, or stops a loop with an `{ "kind": "expr" }` until predicate. With an uncapped loop or a recursive subflow, that makes the format Turing complete: a workflow can carry state and run until the state says to stop, bounded by the run's budgets rather than by its shape.

## Workflow Document Format

Every workflow document is an envelope with a `version` field and a `root` node:

```json
{
  "version": 1,
  "root": { "...": "WorkflowNode" }
}
```

| Field | Type | Description |
|---|---|---|
| `version` | `1` | Schema version. Currently only `1` is supported. |
| `root` | `WorkflowNode` | The top-level node of the workflow tree. |

The `root` node and all descendant nodes are `WorkflowNode` objects, each identified by a `kind` discriminant and a unique `id` string. The document is validated at runtime by `WorkflowDocumentSchema` (a Zod schema exported from `@noetic-tools/core`).

## Published JSON Schema

A standard [JSON Schema (draft 2020-12)](https://json-schema.org/) is generated from `WorkflowDocumentSchema` and published with the package, so editors, CI, and LLM planners can validate documents without importing the runtime. It is available at the `./schema` subpath and on disk at `@noetic-tools/core/schema`:

```jsonc
{
  // your-workflow.json
  "$schema": "https://noetic.tools/schema/noetic-workflow.schema.json",
  "version": 1,
  "root": { "kind": "callModel", "id": "answer", "instructions": "..." }
}
```

Point your editor or validator at the bundled file (resolve it from the package, e.g. `require.resolve('@noetic-tools/core/schema')`) to get autocompletion and inline errors while authoring workflows by hand or reviewing LLM-generated ones. The schema is regenerated from the Zod source via `bun run gen:schema`; a drift-gate test fails CI if the committed artifact falls out of sync.

## Node Kinds

Fourteen node kinds are available, plus the `acp-agent` kind documented in [ACP Agent Steps](/docs/framework/acp-agents). Leaf nodes (`callModel`, `invokeTool`, `runCode`, `compute`, `decide`) perform work; structural nodes (`sequence`, `inParallel`, `conditional`, `routeSwitch`, `loop`, `spawn`, `withContext`, `schedule`, `subflow`) compose them into trees.

Every node takes two optional replay fields — see [Replay Identity](/docs/framework/durability#replay-identity):

| Field | Type | Effect |
|---|---|---|
| `durable` | `boolean` | `false` on cheap orchestration nodes makes a resumed run re-run them instead of replaying their recorded output. |
| `replayKey` | `true \| { from: string[] }` | Replay the node by its input rather than its position. `true` keys on the whole input; `from` keys on those top-level properties of the input parsed as JSON (the same lookup `over` uses). Ignored when `durable` is `false`. |

The key is the node id plus a hash of the selected input, so two different nodes never share an entry, while nodes that share an id do — write the same leaf id into several worker paths and each worker replays its own batch's answer whichever path picks it up:

```json
{
  "kind": "sequence", "id": "worker-a", "durable": false,
  "steps": [
    { "kind": "invokeTool", "id": "worker-a-pick", "toolName": "pick-batch", "durable": false },
    { "kind": "callModel", "id": "grade", "instructions": "Grade this batch.", "replayKey": true }
  ]
}
```

With `from`, a node whose input is not a JSON object logs a warning (`INVALID_REPLAY_KEY_INPUT`) and runs without replay. Inside a dynamic `inParallel` (`each`), node ids get the item index appended, so a keyed node there replays only when its item keeps its index.

### callModel

Call an LLM with instructions and optional tools. Every `tools` entry is a uniform object `{ type, parameters? }`. The `type` value decides the entry: a **registered tool name** (a client tool resolved from the tool registry) or a reserved **server-tool** type the provider executes itself (web search, web fetch).

```json
{
  "kind": "callModel",
  "id": "summarize",
  "model": "openai/gpt-4o",
  "instructions": "Summarize the input text in three bullet points",
  "tools": [
    { "type": "myClientTool" },
    { "type": "openrouter:web_search", "parameters": { "maxResults": 6, "searchContextSize": "medium" } }
  ],
  "params": { "temperature": 0.3, "maxTokens": 1024 }
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `model` | `string` | `'openai/gpt-4o'` | Model identifier (OpenRouter format). |
| `instructions` | `string` | required | System/user prompt for the LLM. |
| `tools` | `{ type: string, parameters?: object }[]` | `undefined` | Uniform tool entries. **Client tool**: `{ "type": "<registered-tool-name>" }` — `type` is resolved against the registry; any `parameters` is ignored (the model supplies call args at runtime). **Server tool**: `{ "type": "openrouter:web_search" \| "openrouter:web_fetch", "parameters"?: {...} }` — run by the provider; `parameters` keys are camelCase (e.g. `maxResults`, `searchContextSize`), unknown keys dropped. Client vs server is decided by the `type` value. |
| `params` | `object` | `undefined` | Model parameters: `temperature`, `topP`, `maxTokens`, `serviceTier` (`auto`, `default`, `fast`, `flex`, `priority`, `scale`, `ultrafast`). `stopSequences` is accepted but deprecated and never sent. |

### runCode

Run a serialised code body. Unlike the programmatic `runCode` (which carries a closure), the JSON form carries `execute` as a code **string**. The code is never `eval`'d in-process (Cloudflare Workers forbid `eval`); it is dispatched through a [subprocess adapter](/docs/framework/runtime) which runs the code and returns its stdout as the step output. The step input is passed to the subprocess on stdin.

```json
{
  "kind": "runCode",
  "id": "transform",
  "execute": "const input = require('fs').readFileSync(0, 'utf8'); process.stdout.write(input.toUpperCase());",
  "retry": { "maxAttempts": 3, "backoff": "exponential", "initialDelay": 100 },
  "subprocess": "sandbox"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `execute` | `string` | required | Source code dispatched to the subprocess. Receives the step input on stdin; its stdout becomes the step output. |
| `retry` | `object` | `undefined` | Retry policy: `{ maxAttempts, backoff: 'fixed' \| 'linear' \| 'exponential', initialDelay, maxDelay? }`. |
| `subprocess` | `string` | `undefined` | Named subprocess adapter ref, resolved via `HydrationContext.resolveSubprocess`. When omitted, the harness default (`ctx.subprocess`) is used. |

> **Execution requires a subprocess adapter.** The `runCode` node does not execute code in the worker process. The host must supply a subprocess adapter capable of running the code body and capturing its stdout. A non-zero exit (or failed handle) surfaces as a thrown error.

### invokeTool

Invoke a registered tool directly.

```json
{
  "kind": "invokeTool",
  "id": "calc-step",
  "toolName": "calculator",
  "args": { "expression": "2 + 2" }
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `toolName` | `string` | required | Name of a tool in the tool registry. |
| `args` | `Record<string, unknown>` | `{}` | Arguments passed to the tool's `execute` function. |

### compute

Compute a value from the input with a [JSONata](https://jsonata.org) expression, with no LLM and no subprocess. The input is read as JSON when it parses, else used as the raw string.

```json
{
  "kind": "compute",
  "id": "step",
  "expr": "{ 'n': n - 1, 'sum': sum + n }"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `expr` | `string` | required | A JSONata expression, evaluated against the input. Must parse: a syntax error fails the document with `WORKFLOW_VALIDATION_FAILED` before anything runs. |

A string result stays a string; any other value is written as JSON (`null` as the empty string). The next node reads that JSON back as data, so a chain of `compute` nodes, or a `loop` whose body is one, carries a state object from step to step. This loop sums 1 to `n` and stops once the state says `done`:

```json
{
  "kind": "loop",
  "id": "count",
  "body": {
    "kind": "compute",
    "id": "step",
    "expr": "n = 0 ? { 'done': true, 'sum': sum } : { 'n': n - 1, 'sum': sum + n }"
  },
  "until": { "kind": "outputContains", "marker": "done" }
}
```

With input `{"n":5,"sum":0}` it outputs `{"done":true,"sum":15}`.

A string result that is itself valid JSON (`"5"`, `"true"`) reads back as that value at the next node; keep strings inside an object to carry them as strings. A result with no JSON form fails the node with `EXPRESSION_FAILED`: JSONata's "no value" (a path that matched nothing) or a function anywhere in the result.

### sequence

Run steps sequentially, threading each output as the next step's input.

```json
{
  "kind": "sequence",
  "id": "pipeline",
  "steps": [
    { "kind": "callModel", "id": "step-1", "instructions": "Extract key facts" },
    { "kind": "callModel", "id": "step-2", "instructions": "Write a summary from the facts above" }
  ]
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `steps` | `WorkflowNode[]` | required | Ordered list of child nodes (min 1). |

### inParallel

Run multiple paths concurrently with configurable merge strategy. A fork is either **static** (a fixed `paths` array) or **dynamic** (`each`: one child per item of a runtime-produced array). Supply exactly one of `paths` or `each`.

```json
{
  "kind": "inParallel",
  "id": "parallel-search",
  "mode": "all",
  "paths": [
    { "kind": "callModel", "id": "search-a", "instructions": "Search topic A" },
    { "kind": "callModel", "id": "search-b", "instructions": "Search topic B" }
  ],
  "merge": "concat",
  "concurrency": 3
}
```

Dynamic fan-out — one child per array item (data-dependent N):

```json
{
  "kind": "inParallel",
  "id": "per-item",
  "mode": "all",
  "over": "items",
  "each": { "kind": "callModel", "id": "worker", "instructions": "Process this item" },
  "merge": "concat"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `mode` | `'all' \| 'race' \| 'settle'` | required | `all` waits for every path; `race` returns the first; `settle` waits for all but tolerates failures. |
| `paths` | `WorkflowNode[]` | — | Static child nodes to execute concurrently. Mutually exclusive with `each`. |
| `each` | `WorkflowNode` | — | Dynamic body template instantiated once per input array item. Each item is injected as that child's input; template node ids are suffixed `-<i>` for uniqueness. Mutually exclusive with `paths`. |
| `over` | `string` | `undefined` | With `each`: selector key into the input JSON object locating the array. When omitted, the input string is parsed as a JSON array directly. |
| `merge` | `'last' \| 'first' \| 'concat'` | `'last'` | How to combine results. `concat` writes object results (such as a `decide` node's answers) as JSON. Ignored in `race` mode. |
| `concurrency` | `number` | `undefined` | Maximum concurrent paths. |

### conditional

Route input to one of several targets. Each route tests the input with either a substring (`match`) or an [expression](/docs/framework/expressions) (`expr`).

```json
{
  "kind": "conditional",
  "id": "router",
  "routes": [
    { "match": "code", "target": { "kind": "callModel", "id": "code-path", "instructions": "Write code" } },
    { "match": "explain", "target": { "kind": "callModel", "id": "explain-path", "instructions": "Explain the concept" } }
  ],
  "default": { "kind": "callModel", "id": "fallback", "instructions": "Handle the request" }
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `routes` | `({ match: string } \| { expr: string })` plus `target: WorkflowNode`, as an array | required | Ordered routes, each with exactly one test. The first route whose test passes wins. |
| `default` | `WorkflowNode` | `undefined` | Fallback node when no route matches. |

When the input is an object, or a string holding a JSON object or array (such as a `decide` node's answers passed on by a `sequence`), routes match against its string values only, not its keys. For answers, those are each answer's `type` (so `"refusal"` matches a refusal), a choice's `value`, and a score's `level`. A `decide` node's answers name every choice in their keys and probability maps, so matching the raw JSON would hit every route. Boolean answers have no string value to match; route on those with `routeSwitch`.

#### Expression routes

`match` suits prose. For structured state, give a route an `expr` instead: a JSONata test run against the input, parsed as JSON when it parses (else the raw string). The route is taken if the test gives `true` and skipped if it gives `false` or no value, such as a path that matches nothing. Any other result, like a number or a string, fails the run with `EXPRESSION_FAILED`; an `expr` that does not parse fails validation with `WORKFLOW_VALIDATION_FAILED` before anything runs. A route with both `match` and `expr`, or neither, fails schema validation.

```json
{
  "kind": "conditional",
  "id": "size",
  "routes": [
    { "expr": "n = 0", "target": { "kind": "callModel", "id": "empty", "instructions": "Say there is nothing to do." } },
    { "match": "urgent", "target": { "kind": "callModel", "id": "rush", "instructions": "Handle this now." } },
    { "expr": "n > 3", "target": { "kind": "callModel", "id": "batch", "instructions": "Split the work into batches." } }
  ],
  "default": { "kind": "callModel", "id": "small", "instructions": "Do the work." }
}
```

Both kinds mix in one node and run in order. An `expr` can also read a `decide` node's answers, including boolean ones: after a `decide` asking `refund` in a `sequence`, `"expr": "refund.value"` takes the route on a yes.

An `expr` route makes a clean base case for a recursive named workflow. This `countdown` adds `n` to `total` and calls itself until `n` is 0:

```json
{
  "version": 1,
  "root": {
    "kind": "conditional",
    "id": "check",
    "routes": [
      { "expr": "n = 0", "target": { "kind": "compute", "id": "done", "expr": "{ \"total\": total }" } }
    ],
    "default": {
      "kind": "sequence",
      "id": "step",
      "steps": [
        { "kind": "compute", "id": "next", "expr": "{ \"n\": n - 1, \"total\": total + n }" },
        { "kind": "subflow", "id": "again", "ref": "countdown" }
      ]
    }
  }
}
```

Run with input `{"n":4,"total":0}`, it outputs `{"total":10}`.

### decide

Ask a model typed questions about the context. Hydrates into [`decide`](/docs/framework/steps/decide). Questions are plain JSON, in the same shape as the programmatic API.

```json
{
  "kind": "decide",
  "id": "triage",
  "model": "typesafe/jev-1.14",
  "instructions": "Support ticket triage.",
  "questions": {
    "destination": {
      "type": "choice",
      "instructions": "Which team should handle this ticket?",
      "choices": { "billing": "Refunds, invoices", "support": "Bugs, outages" }
    },
    "isUrgent": { "type": "boolean", "instructions": "Is the customer reporting downtime?" }
  },
  "view": "full"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `model` | `string` | harness `decisionModel` | Decision or chat model id. |
| `instructions` | `string` | `undefined` | Shared framing for every question. |
| `questions` | `Record<string, DecideQuestion>` | required | `boolean`, `choice`, and `score` questions keyed by id. Validated by the same rules as `decide()`. |
| `view` | `'full' \| 'layers' \| 'none'` | `'full'` | How much of the assembled view the model sees. |
| `samples` | `number` | `1` | Positive integer. Runs to average on the estimated path. |

A `decide` node outputs the answers object. Inside a `sequence`, the next node receives it as JSON, so a `callModel` node can read it. A `conditional` matches against the answers' string values, and a `inParallel` with `merge: "concat"` writes them as JSON. The `context` selector is a closure and has no JSON form.

### routeSwitch

Run a `decide` node and route the original input to the case its answer picks. Hydrates into the key form of [`routeSwitch`](/docs/framework/operators/route-switch).

```json
{
  "kind": "routeSwitch",
  "id": "route-ticket",
  "decide": {
    "kind": "decide",
    "id": "triage",
    "model": "typesafe/jev-1.14",
    "questions": {
      "destination": { "type": "choice", "choices": ["billing", "support"] }
    }
  },
  "on": "destination",
  "cases": {
    "billing": { "kind": "callModel", "id": "billing", "instructions": "Resolve the billing question" },
    "support": { "kind": "callModel", "id": "support", "instructions": "Debug the reported problem" }
  },
  "minConfidence": 0.6,
  "uncertain": { "kind": "callModel", "id": "ask-human", "instructions": "Ask a human to triage this ticket" }
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `decide` | `DecideWorkflowNode` | required | The decision to route by. |
| `on` | `string` | required | Id of the question to route by. |
| `cases` | `Record<string, WorkflowNode>` | required | One node per outcome of `on`: each choice, `"true"` and `"false"` for a boolean, or each level label for a score. |
| `minConfidence` | `number` | `undefined` | In `[0, 1]`. Below this confidence, take `uncertain`. |
| `uncertain` | `WorkflowNode` | required | Taken on refusal or low confidence. |

Schema validation checks that `on` names a question of the `decide` node, that `cases` covers every outcome of that question, and that `uncertain` is present. Only the key form has a JSON node; the function form of `on` is a closure.

### loop

Repeat a body node until a predicate is satisfied.

```json
{
  "kind": "loop",
  "id": "refine",
  "body": { "kind": "callModel", "id": "refine-step", "instructions": "Improve the draft" },
  "until": { "kind": "maxSteps", "n": 5 },
  "maxIterations": 10
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `body` | `WorkflowNode` | required | The node to repeat. |
| `until` | `UntilPredicate` | required | Termination condition. See [Until Predicates](#until-predicates). |
| `maxIterations` | `number \| "infinity"` | `1000` | Hard cap on iterations: a positive integer, or exactly `"infinity"` for none. |

JSON cannot encode `Infinity`, so an uncapped loop spells it `"infinity"`; the hydrator maps it to `Number.POSITIVE_INFINITY`. An uncapped loop ends only through its `until` predicate, an error, or an aborted context, so pair it with a predicate the body's output can satisfy:

```json
{
  "kind": "loop",
  "id": "work-until-done",
  "body": { "kind": "callModel", "id": "work", "instructions": "Take the next step" },
  "until": {
    "kind": "decide",
    "id": "finished",
    "questions": {
      "done": { "type": "boolean", "instructions": "Is the task finished?" }
    }
  },
  "maxIterations": "infinity"
}
```

### spawn

Run a child node in an isolated child context.

```json
{
  "kind": "spawn",
  "id": "background-task",
  "child": { "kind": "callModel", "id": "worker", "instructions": "Process in background" },
  "timeout": 30000
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `child` | `WorkflowNode` | required | The node to execute in a child context. |
| `timeout` | `number` | `undefined` | Timeout in milliseconds. |
| `layers` | `string[]` | `undefined` | Context layer names for the child, resolved from the hydration context registry (same resolution as `withContext`). Omit to inherit the parent's layers; naming layers **replaces** them for the child. |

```json
{
  "kind": "spawn",
  "id": "worker",
  "child": { "kind": "callModel", "id": "work", "instructions": "Do the unit of work" },
  "layers": ["task-state"]
}
```

### withContext

Wrap a child node with context layers.

```json
{
  "kind": "withContext",
  "id": "with-memory",
  "child": { "kind": "callModel", "id": "agent", "instructions": "..." },
  "layers": ["conversation-summary"]
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `child` | `WorkflowNode` | required | The node to wrap. |
| `layers` | `string[]` | required | Layer names. Currently layers are referenced by name but not resolved from a registry -- the harness's default layers are inherited instead. |

### schedule

Execute a step on a fixed interval (periodic scheduling).

```json
{
  "kind": "schedule",
  "id": "heartbeat",
  "step": { "kind": "callModel", "id": "check", "instructions": "Check system status" },
  "interval": 60000,
  "onError": "continue"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `step` | `WorkflowNode` | required | The node to execute each interval. |
| `interval` | `number` | required | Interval in milliseconds. |
| `onError` | `'continue' \| 'fail'` | `undefined` | Whether to keep running or abort on error. |

### subflow

Run another workflow document as a single step — inline, or by name resolved from the `workflows` registry.

```json
{
  "kind": "subflow",
  "id": "verify",
  "ref": "verify-loop"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | `string` | required | Unique step identifier. |
| `document` | `WorkflowDocument` | XOR | Inline sub-workflow. Supply exactly one of `document` / `ref`. |
| `ref` | `string` | XOR | Named sub-workflow resolved from `HydrationContext.workflows` (or the `workflows` option on `parseAndRunWorkflow`). |
| `input` | `string` | `undefined` | Literal input for the sub-workflow; defaults to the node's runtime input. |

Resolution is lazy — the target document resolves and hydrates on first execution, so a live registry may gain entries after hydration. An unregistered name raises `UNKNOWN_WORKFLOW_REFERENCE`. Two subflow nodes referencing the same workflow are fine — the sub-tree's node ids are suffixed with the subflow node's id so traces stay distinct.

#### Recursion

Named workflows may call themselves, directly or through other named workflows. A subflow node without `input` passes its runtime input on, so the steps before a recursive call compute what it receives, and a routing node such as `conditional` picks the base case:

```json
{
  "version": 1,
  "root": {
    "kind": "sequence",
    "id": "body",
    "steps": [
      { "kind": "runCode", "id": "step", "execute": "<count down; print done at zero>" },
      {
        "kind": "conditional",
        "id": "check",
        "routes": [{ "match": "done", "target": { "kind": "runCode", "id": "finish", "execute": "<report>" } }],
        "default": { "kind": "subflow", "id": "recurse", "ref": "countdown" }
      }
    ]
  }
}
```

Each recursion level hydrates lazily into its own tree, with ids suffixed by the calling subflow node's id (`body-top`, `body-recurse-top`, …), so every level traces and replays under distinct step ids. Depth is bounded at execution time: when a ref would resolve more than `maxRecursionDepth` levels deep on one path (default `100`; `Infinity` for no limit), the call throws `WORKFLOW_RECURSION_LIMIT`.

## Until Predicates

Loop termination conditions are expressed as named predicates. Each predicate is a JSON object with a `kind` discriminant. See [Loop & Until](/docs/framework/operators/loop-and-until) for the programmatic equivalents.

### Named predicates

| Kind | Fields | Description |
|---|---|---|
| `maxSteps` | `n: number` | Stop after `n` iterations. |
| `maxCost` | `usd: number` | Stop when cumulative cost exceeds `usd` dollars. |
| `maxDuration` | `duration: number` | Stop after `duration` milliseconds. |
| `noToolCalls` | -- | Stop when the LLM produces no tool calls in a round. |
| `outputContains` | `marker: string` | Stop when output contains the marker substring. |
| `outputEquals` | `sentinel: string` | Stop when output exactly equals the sentinel. |
| `converged` | `threshold?: number` | Stop when output similarity between rounds exceeds `threshold` (0-1, defaults to the builder default). |
| `never` | -- | Never stop; the loop ends on its `maxIterations` cap, an error, or an aborted context. |
| `expr` | `expr: string` | Stop when a [JSONata expression](/docs/framework/expressions) over the iteration's output gives `true`. |
| `decide` | a [decide node](#decide) | A model answers one boolean question about the iteration's output: yes stops, no or a refusal continues. |

### Decide as a predicate

A plain [decide node](#decide) can end a loop. It must ask exactly one question, and that question must be boolean; schema validation rejects anything else. Each iteration it runs on the loop's last output (and, like any decide node, sees the context view without writing to it): a yes stops the loop, a no or a refusal runs another iteration. With `"maxIterations": "infinity"`, a model that keeps refusing keeps the loop running until the context is aborted, so put a backstop beside it when that matters:

```json
{
  "kind": "any",
  "predicates": [
    { "kind": "maxSteps", "n": 20 },
    {
      "kind": "decide",
      "id": "good-enough",
      "questions": {
        "ship": { "type": "boolean", "instructions": "Is the draft ready to ship?" }
      }
    }
  ]
}
```

A decide node inside `until` is part of the workflow tree: `walkWorkflow` and `workflowGraph` list it as a child of its loop, and subflow and `each` id suffixes apply to it like any other node.

### Expression as a predicate

An `expr` predicate evaluates a [JSONata expression](/docs/framework/expressions) against the loop's last output. An output string that holds JSON is parsed first, so a body that returns a state object can be tested field by field. `true` stops the loop; `false`, or no value (a path that matches nothing), runs another iteration:

```json
{
  "kind": "loop",
  "id": "drain",
  "body": { "kind": "compute", "id": "step", "expr": "{ \"n\": n - 1 }" },
  "until": { "kind": "expr", "expr": "n = 0" },
  "maxIterations": "infinity"
}
```

The expression must give a boolean. Any other value, or an expression that fails at run time, fails the loop with `EXPRESSION_FAILED` rather than stopping it, so a mistyped test never passes off the last output as the result. A syntax error fails the whole document with `WORKFLOW_VALIDATION_FAILED` before anything runs, wherever the predicate sits, `any` and `all` included.

### Combinators

Combine multiple predicates with `any` (logical OR) or `all` (logical AND):

```json
{
  "kind": "any",
  "predicates": [
    { "kind": "maxSteps", "n": 10 },
    { "kind": "outputContains", "marker": "DONE" }
  ]
}
```

```json
{
  "kind": "all",
  "predicates": [
    { "kind": "maxSteps", "n": 3 },
    { "kind": "noToolCalls" }
  ]
}
```

## dynamicWorkflow()

The `dynamicWorkflow` pattern hands the planning to an LLM: it generates a workflow document as JSON, validates it, hydrates it, and executes it -- all within a single harness run. If validation fails, the planner retries with error feedback up to `maxRevisions` times.

```ts
import { dynamicWorkflow, AgentHarness, type Tool } from '@noetic-tools/core';

declare const searchTool: Tool;
declare const calcTool: Tool;

const agent = dynamicWorkflow({
  model: 'openai/gpt-4o',
  tools: [searchTool, calcTool],
  instructions: 'Plan the most efficient workflow',
  maxDepth: 5,
});

const harness = new AgentHarness({
  name: 'planner',
  agentGraph: agent,
  params: {},
});

await harness.execute('Research and summarize quantum computing advances');
const response = await harness.getAgentResponse();
```

### DynamicWorkflowOpts

| Field | Type | Default | Description |
|---|---|---|---|
| `model` | `string` | `'openai/gpt-4o'` | Model for the planner LLM. |
| `instructions` | `string` | `undefined` | Additional instructions prepended to the planner prompt. |
| `tools` | `Tool[]` | required | Tools the generated workflow may reference by name. |
| `maxDepth` | `number` | `5` | Maximum allowed tree depth for generated workflows. |
| `maxRevisions` | `number` | `3` | Retries with error feedback on validation failure. |

Throws `NoeticConfigError` with code `WORKFLOW_VALIDATION_FAILED` if the planner cannot produce a valid workflow within the revision limit.

## parseAndRunWorkflow()

For pre-built JSON workflows -- parse, validate, hydrate, and execute in one call.

```ts
import { parseAndRunWorkflow, AgentHarness, type Tool } from '@noetic-tools/core';

declare const workflowDocument: unknown;
declare const searchTool: Tool;
declare const calcTool: Tool;

const harness = new AgentHarness({ name: 'runner', params: {} });
const ctx = harness.createContext();

const result = await parseAndRunWorkflow({
  json: workflowDocument,
  harness,
  ctx,
  tools: [searchTool, calcTool],
  maxDepth: 5,
});
```

### ParseAndRunWorkflowOpts

| Field | Type | Default | Description |
|---|---|---|---|
| `json` | `unknown` | required | Raw JSON (string or parsed object) representing a workflow document. |
| `harness` | `AgentHarnessContract` | required | The [AgentHarness](/docs/framework/runtime) to execute the workflow with. |
| `ctx` | `Context` | required | Execution context. |
| `tools` | `Tool[]` | required | Available tools the workflow may reference by name. |
| `maxDepth` | `number` | `5` | Maximum allowed workflow tree depth. |
| `layers` | `ReadonlyMap<string, ContextLayer>` | `undefined` | Named context layers that `withContext`/`spawn` nodes may reference. |
| `workflows` | `ReadonlyMap<string, WorkflowDocument>` | `undefined` | Named sub-workflows that `subflow` nodes may reference via `ref`. |
| `maxRecursionDepth` | `number` | `100` | Deepest chain of named-ref resolutions on one path. A positive integer or `Infinity`. |

Returns `Promise<string>` -- the string output of the executed workflow.

Throws `NoeticConfigError` with code `WORKFLOW_VALIDATION_FAILED` if the JSON does not match `WorkflowDocumentSchema`. Throws `NoeticConfigError` with code `UNKNOWN_TOOL_REFERENCE` if a tool name cannot be resolved.

## Worked example: a model panel with an Opus judge

A complete, runnable example lives at [`packages/core/examples/dynamic-judge-workflow.ts`](https://github.com/mattapperson/noetic/blob/main/packages/core/examples/dynamic-judge-workflow.ts). An Opus planner *generates* a workflow as JSON, the document is validated, and then it is executed: the question fans out to four different models in parallel (an `inParallel` node with `mode: "settle"`), and their concatenated answers are piped to an Opus judge that synthesises a single ideal response — the "mixture-of-agents" pattern, expressed entirely as data.

```bash
OPENROUTER_API_KEY=sk-... bun examples/dynamic-judge-workflow.ts "Your question here"
```

The canonical, hand-checked version of the generated document is committed at [`packages/core/examples/multi-model-judge.workflow.json`](https://github.com/mattapperson/noetic/blob/main/packages/core/examples/multi-model-judge.workflow.json):

```json
{
  "$schema": "https://noetic.tools/schema/noetic-workflow.schema.json",
  "version": 1,
  "root": {
    "kind": "sequence",
    "id": "multi-model-judge",
    "steps": [
      {
        "kind": "inParallel",
        "id": "panel",
        "mode": "settle",
        "merge": "concat",
        "paths": [
          { "kind": "callModel", "id": "answer-gpt", "model": "openai/gpt-4.1", "instructions": "Answer the question. Prefix with '## Candidate (openai/gpt-4.1)'." },
          { "kind": "callModel", "id": "answer-gemini", "model": "google/gemini-2.5-pro", "instructions": "Answer the question. Prefix with '## Candidate (google/gemini-2.5-pro)'." },
          { "kind": "callModel", "id": "answer-llama", "model": "meta-llama/llama-3.3-70b-instruct", "instructions": "Answer the question. Prefix with '## Candidate (meta-llama/llama-3.3-70b-instruct)'." },
          { "kind": "callModel", "id": "answer-deepseek", "model": "deepseek/deepseek-chat", "instructions": "Answer the question. Prefix with '## Candidate (deepseek/deepseek-chat)'." }
        ]
      },
      {
        "kind": "callModel",
        "id": "judge",
        "model": "anthropic/claude-opus-4.5",
        "instructions": "Compare the candidate answers, correct any errors, and output one synthesised best answer."
      }
    ]
  }
}
```

`mode: "settle"` is deliberate: a single flaky provider cannot abort the whole panel, and the judge synthesises from whichever candidates responded.

## Hydration API

For lower-level control, use `hydrateWorkflow` and `hydrateNode` to convert JSON workflow structures into live `Step` objects without immediately executing them.

```ts validate=none
import { hydrateWorkflow, hydrateNode } from '@noetic-tools/core';
import type { HydrationContext } from '@noetic-tools/core';

const hydrationCtx: HydrationContext = {
  tools: new Map(myTools.map((t) => [t.name, t])),
  executeStep: harness.run.bind(harness),
};

// Hydrate an entire document
const rootStep = hydrateWorkflow(workflowDoc, hydrationCtx);

// Or hydrate a single node
const singleStep = hydrateNode(someNode, hydrationCtx);

// Then execute manually
const result = await harness.run(rootStep, 'input text', ctx);
```

### HydrationContext

| Field | Type | Description |
|---|---|---|
| `tools` | `ReadonlyMap<string, Tool>` | Tool registry mapping tool names to `Tool` instances. |
| `executeStep` | `ExecuteStepFn` | Step executor function (typically `harness.run.bind(harness)`). |
| `layers` | `ReadonlyMap<string, ContextLayer>` | Optional. Named context layers that `withContext`/`spawn` nodes reference; an unknown name raises `UNKNOWN_LAYER_REFERENCE`. Without a registry, those nodes run with the harness-default layers. |
| `acpAgents` | `ReadonlyMap<string, AcpAgent>` | Optional. ACP agent adapters keyed by `agentId`, resolving an `acp-agent` node's `agent` field. |
| `uiLibraries` | `ReadonlyMap<string, OutputCodec>` | Optional. Output codecs for `callModel` nodes' `output` codec references. |
| `resolveSubprocess` | `(ref: string) => SubprocessAdapter \| undefined` | Optional. Resolves a `runCode` node's named `subprocess` ref to an adapter. When a `runCode` node omits the ref, the harness default (`ctx.subprocess`) is used at execution time. |
| `workflows` | `ReadonlyMap<string, WorkflowDocument>` | Optional. Named sub-workflow documents that `subflow` nodes resolve via `ref` — lazily, so a live map may gain entries after hydration. |
| `maxRecursionDepth` | `number` | Optional. Deepest chain of named-ref resolutions on one path; default `100`, `Infinity` for none. |

`hydrateWorkflow(doc, ctx)` converts a validated `WorkflowDocument` into its root `Step`. `hydrateNode(node, ctx)` converts a single `WorkflowNode`. Both return `Step<ContextData, string, string>` -- indistinguishable from programmatically built steps.

Throws `NoeticConfigError` with code `UNKNOWN_NODE_KIND` if a node kind is unrecognised, `UNKNOWN_TOOL_REFERENCE` if a tool name cannot be resolved, `UNKNOWN_UNTIL_PREDICATE` if an until predicate kind is unrecognised, or `INVALID_UNTIL_DECIDER` if a decide predicate does not ask exactly one boolean question. At execution time a `subflow` ref can raise `UNKNOWN_WORKFLOW_REFERENCE`, `WORKFLOW_RECURSION_LIMIT`, or `INVALID_MAX_RECURSION_DEPTH`.

## Limitations

- **`runCode` nodes need a subprocess adapter** -- the JSON `runCode` node carries its body as a code string and dispatches it through a subprocess adapter (it is never `eval`'d in-process). A host that uses `runCode` nodes must supply an adapter capable of running the code and capturing its stdout.
- **Tools resolved by name** -- every tool referenced in the workflow must be passed in the `tools` array. The hydrator looks them up by `tool.name`.
- **Subflow refs resolve at execution time** -- a `subflow` node's `ref` is looked up on first execution, not during hydration, so an unregistered name surfaces as `UNKNOWN_WORKFLOW_REFERENCE` when the node runs. Depth limits do not see through refs; `maxRecursionDepth` bounds the depth of any one recursive path, but not total fan-out — hosts should keep it finite and cap registry size and breadth for untrusted documents.
- **Unbounded control flow is opt-in** -- `"maxIterations": "infinity"` and `maxRecursionDepth: Infinity` remove the runtime's bounds. A host that runs untrusted documents and must bound every loop should reject `"infinity"` before hydrating.
- **Conditional routes test, they do not compute** -- a `conditional` route is a substring `match` or a JSONata `expr` test. Routing that needs to run a step or call a function requires a programmatic `conditional()` step.

## Plans as Workflows

The [plan layer](/docs/framework/context-layers/plan) authors plans directly in this format: the reviewed plan tree is a `WorkflowDocument`, and the plan's named workflows feed the `workflows` registry. Composition also works from code — `workflow` runs a document (inline or by `ref`) as a single composable step:

```ts validate=none
import { workflow } from '@noetic-tools/core';

const verify = workflow({
  id: 'verify',
  ref: 'verify-loop',
  workflows: new Map([['verify-loop', verifyDoc]]),
  tools: [testRunnerTool],
  isolation: 'spawn', // optional: run in a fresh context boundary
});
```

`workflow` resolves the document lazily, memoizes the hydrated tree, and requires exactly one of `document` / `ref` (`INVALID_WORKFLOW_SOURCE` otherwise).
