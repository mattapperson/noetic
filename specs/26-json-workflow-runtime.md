# JSON Workflow Runtime

> **Depends On:** `01-step-type` (Step, Until), `02-step-variants` (callModel, invokeTool), `03-control-flow` (conditional, inParallel), `04-spawn` (spawn), `05-loop-and-until` (loop, until), `08-runtime` (AgentHarness), `33-expressions` (Expression)
> **Exports:** `WorkflowDocument`, `WorkflowNode`, `WorkflowDocumentSchema`, `WorkflowNodeSchema`, `UntilPredicateSchema`, `MergeStrategySchema`, `hydrateWorkflow`, `hydrateNode`, `dynamicWorkflow`, `parseAndRunWorkflow`, `RunCodeGrant`

---

## Motivation

Step trees in noetic are built programmatically: TypeScript code calls builders like `callModel(...)`, `loop(...)`, `inParallel(...)` and wires them together at compile time. This works when the workflow shape is known ahead of time.

But many agent patterns need the shape to emerge at runtime:

1. **Plan-then-execute** -- An LLM generates a multi-step plan as structured output, then the harness executes it. The plan shape is not known until the model responds.
2. **Portable workflows** -- JSON documents can be stored in databases, passed between processes, shared across language boundaries, and audited after the fact. Closures cannot.
3. **User-authored workflows** -- End users or low-code tools define agent behavior as JSON configuration without writing TypeScript.
4. **Replay and inspection** -- A JSON workflow is a complete, inspectable record of what the agent intended to do, independent of execution state.

The JSON Workflow Runtime bridges these worlds: an LLM (or any producer) emits a `WorkflowDocument`, the runtime validates it, hydrates it into a native `Step` tree, and executes it with the same interpreter, context layers, and observability as hand-written compositions.

## Workflow Document Format

A workflow document is a versioned envelope around a single root node:

```typescript
interface WorkflowDocument {
  version: 1;
  customItems?: Record<string, WorkflowCustomItem>;
  connections?: Record<string, WorkflowConnectionRequirement>;
  root: WorkflowNode;
}
```

`connections` lists the connections the document needs, each with a semver
range for its profile and extensions (or the events a source must offer);
every operation and event a node uses must come from it, and a host allowlist
bounds what a document may ask for. See `35-connections` § JSON workflows.

The `version` field enables forward-compatible parsing. Consumers reject documents with an unrecognised version rather than silently misinterpreting them.

```typescript
const WorkflowDocumentSchema = z.object({
  version: z.literal(1),
  root: WorkflowNodeSchema,
});
```

### Published JSON Schema

`WorkflowDocumentSchema` is the single source of truth. A standard JSON Schema (draft 2020-12) is serialised from it and published with the package so external tooling — editors, CI validators, and LLM planners — can validate documents without importing the runtime.

- The artifact is committed at `packages/core/schema/noetic-workflow.schema.json` and exposed at the `@noetic-tools/core/schema` export subpath. Its stable `$id` is `https://noetic.tools/schema/noetic-workflow.schema.json`, which resolves: a byte-identical copy is served by the web app from `packages/web/public/schema/noetic-workflow.schema.json`.
- It is generated by `bun run gen:schema` (`scripts/generate-workflow-schema.ts`), which calls `z.toJSONSchema(WorkflowDocumentSchema, { target: 'draft-2020-12' })` and writes both the published core artifact and the hosted web copy. The recursive types — `WorkflowNode`, `UntilPredicate`, and `Expression` (spec 33), plus the `JsonValue` that an expression's `quote` holds — are emitted as named `$defs`; every other subschema is inlined.
- A drift-gate test re-serialises the schema and asserts both committed copies are byte-for-byte current, and that the published variants cover exactly the runtime node and predicate kinds. CI fails if `gen:schema` was not re-run after a schema change.

Authoring documents by hand or reviewing LLM-generated ones, reference the schema with a `$schema` key so editors surface autocompletion and inline errors:

```jsonc
{
  "$schema": "https://noetic.tools/schema/noetic-workflow.schema.json",
  "version": 1,
  "root": { "kind": "callModel", "id": "answer", "instructions": "..." }
}
```

## WorkflowNode Union

`WorkflowNode` is a discriminated union on `kind`. Each variant maps to an existing `Step` builder. All nodes share six fields: an optional `fromParams` (§ Options from params), and five more: a required `id`, an optional boolean `durable` that the hydrator copies onto the built step, an optional declarative `replayKey` (§ Replay keys) that the hydrator turns into the step's `replayKey` function, an optional `emitItems` (§ Emitting items) that the hydrator turns into the step's `emitItems`, and optional `customItems` that only that node may emit (spec 34). `durable: false` keeps the node out of the step ledger, so a resumed run re-runs it instead of replaying its recorded output (`23a-step-level-resume` § Identity). The `acp-agent` node kind is specified in `27-acp-agent-steps`.

```typescript
type WorkflowNode =
  | CallModelWorkflowNode
  | InvokeToolWorkflowNode
  | RunCodeWorkflowNode
  | ComputeWorkflowNode
  | ConditionalWorkflowNode
  | DecideWorkflowNode
  | RouteSwitchWorkflowNode
  | InParallelWorkflowNode
  | SpawnWorkflowNode
  | WithContextWorkflowNode
  | LoopWorkflowNode
  | SequenceWorkflowNode
  | ScheduleWorkflowNode
  | SubflowWorkflowNode
  | AcpAgentWorkflowNode;
```

### Replay keys

A programmatic step's `replayKey` is a function (`23a-step-level-resume` § Identity); a JSON node cannot carry one. It names instead which part of its input identifies the work, and the hydrator builds the function:

```typescript
type WorkflowReplayKey =
  | true                    // key on the whole input
  | { from: string[] };     // key on these top-level properties of the input, parsed as JSON
```

`from` reads each property the way an `inParallel` node's `over` reads its array: the input is parsed as JSON and the named top-level key is looked up. A replay key is a list of names rather than an expression (spec 33), so the ledger key stays readable and cannot fail to evaluate. A missing property keys as `null`.

The built key is `<node id>:<hash>`, where the hash covers the whole input (`true`) or the JSON list of the selected values (`from`), via `hashString`. Prefixing the node id keeps two different nodes that read the same input — a `grade` and a `summarize` of one batch — from sharing a ledger entry and discarding each other's on every resume. Nodes that share an id share entries, which is how one worker leaf written into several `inParallel` paths finds its batch's answer whichever path runs it:

```json
{
  "kind": "inParallel", "id": "pool", "mode": "all", "durable": false, "merge": "concat",
  "paths": [
    { "kind": "sequence", "id": "worker-a", "durable": false, "steps": [
      { "kind": "runCode", "id": "worker-a-pick", "durable": false, "execute": "…", "subprocess": "sandbox" },
      { "kind": "runCode", "id": "grade", "replayKey": true, "execute": "…", "subprocess": "sandbox" }
    ] },
    { "kind": "sequence", "id": "worker-b", "durable": false, "steps": [
      { "kind": "runCode", "id": "worker-b-pick", "durable": false, "execute": "…", "subprocess": "sandbox" },
      { "kind": "runCode", "id": "grade", "replayKey": true, "execute": "…", "subprocess": "sandbox" }
    ] }
  ]
}
```

`from` on an input that is not a JSON object makes the key function throw `INVALID_REPLAY_KEY_INPUT`; the interpreter treats a throwing `replayKey` as it does for code (warn, run the step without replay or recording), so the node still runs. `replayKey` is ignored on a node that is also `durable: false`.

Inside a dynamic `inParallel` (`each`), the hydrator suffixes every template node id with the item index, and replay matches `stepId` as well as the key. A keyed node there therefore replays only when its item lands at the same index — content keys do not survive a reordered `each` input.

### Emitting items

A workflow's output normally reaches the user only when its last step finishes. `emitItems` makes any node add items to the conversation as it runs (`01-step-type` § Emitting items); the items stream through `getItemStream` at once, so a node inside a loop emits on every iteration, before the loop's `until` stops it and before any later node runs:

```typescript
type WorkflowEmitItems =
  | boolean                       // true: the output is a final item
  | {
      item?: string;              // a declared custom item (spec 34)
      onStart?: Expression;       // read against the input: one event of `item`
      onDone?: Expression;        // read against the output: the final fields, or message text without `item`
    };
```

- **`true`** emits the output as a final item. Output that is JSON text of an object whose `type` names a custom item in the node's scope becomes that item, validated against its `output` schema and given an `id`. Other output becomes an assistant message: a string as is, anything else as JSON text, as in § `compute`.
- **`onStart`** needs an `item` (the schema rejects it without one). Its value is one **event** of the item, validated against the item's `event` schema.
- **`onDone`** with an `item` gives the item's **final fields**. Without one, its value becomes the text of an assistant message.
- An expression that gives no value (a path that matches nothing) emits nothing for that hook, so a node can emit on some iterations and stay quiet on others. A result holding a function fails the node with `EXPRESSION_FAILED`.
- Validation compiles both expressions like any other, so a syntax error fails the document with `WORKFLOW_VALIDATION_FAILED`. The object is strict: an unknown key fails validation.

Custom items are declared in JSON Schema, in the document's root `customItems` map (any node may emit them) or in a node's own `customItems` (only that node may). Declarations, scopes, subflows, and the typed harness results they produce are specified in `34-custom-items`.

```json
{
  "version": 1,
  "customItems": {
    "progress": {
      "type": "myapp:progress",
      "event": { "type": "object", "properties": { "left": { "type": "number" } }, "required": ["left"] },
      "output": { "type": "object", "properties": { "left": { "type": "number" } }, "required": ["left"] }
    }
  },
  "root": {
    "kind": "loop",
    "id": "drain",
    "maxIterations": "infinity",
    "body": {
      "kind": "compute",
      "id": "step",
      "expr": "{ 'n': n - 1 }",
      "emitItems": { "item": "progress", "onStart": "{ 'left': n }", "onDone": "{ 'left': n }" }
    },
    "until": { "kind": "expr", "expr": "n = 0" }
  }
}
```

A resumed run that replays a node, or replays any node above it, puts its emitted items back on the log quietly. The harness option `emitItemsOnReplay` also streams them again (`01-step-type` § On resume). A document has no per-node setting for this.

A `decide` node emits its answers object: `true` emits its JSON, and `onDone` reads it (`"stop.value ? 'done' : 'again'"`). Used as a loop's `until`, it emits after every iteration's verdict. A structural node (`sequence`, `loop`, `subflow`, …) emits its own output once it finishes, after its children have emitted. A `callModel` node's model output is already in the conversation, so `emitItems` on one adds a second message.

### `callModel`

A single LLM call.

```typescript
interface CallModelWorkflowNode {
  kind: 'callModel';
  id: string;
  model?: string;
  instructions: string;
  tools?: Array<
    | { type: string; parameters?: Record<string, unknown> }  // a client or openrouter:* server tool
    | { connection: string; ops?: string[] }                   // a harness or turn connection's tools
    | { mcp: { name: string; url: string; headers?: Array<{ name: string; value: { $secret: string } }> } }
  >;
  toolChoice?: 'auto' | 'required' | 'none' | { tool: string };
  params?: {
    temperature?: number;
    topP?: number;
    maxTokens?: number;
    stopSequences?: string[];  // deprecated: accepted, never sent (spec 02)
    serviceTier?: 'auto' | 'default' | 'fast' | 'flex' | 'priority' | 'scale' | 'ultrafast';
  };
  output?:
    | { schema: Record<string, unknown> }   // structured output, as a JSON Schema
    | { codec: 'openui'; library: string }; // a streaming codec, by registry key (spec 28)
}
```

| Field          | Required | Description                                              |
|----------------|----------|----------------------------------------------------------|
| `model`        | No       | Model identifier. Falls back to the harness `model` (`08-runtime`), read when the node runs, and to `openai/gpt-4o` on a harness that sets none. |
| `instructions` | No       | System instructions for this LLM call.                   |
| `tools`        | No       | Tool entries: `{ "type" }` names a registered client tool or an `openrouter:*` server tool; `{ "connection" }` and `{ "mcp" }` give the model a connection's tools (§ Tools). |
| `toolChoice`   | No       | How the model may use its tools (spec 02, Unified Tool Set). Defaults to `"auto"`. `{ "tool": name }` must name a client tool in `tools`, or hydration throws `UNKNOWN_TOOL_CHOICE`; without `tools` it is checked against the unified set at request time. |
| `params`       | No       | Model-level sampling parameters.                         |
| `output`       | No       | Structured output (§ Structured output), or a streaming codec reference resolved from `uiLibraries`. |
| `emit`         | No       | `false` keeps the step's framework events out of the stream. Default `true`. |
| `projection`   | No       | How this call's context window is fitted: `{ tokenBudget, responseReserve, overflow, overflowModel?, windowSize? }`. Overrides the harness default (spec 11). |

`instructions` is optional, as it is on `callModel()`. `model`, `instructions`, `tools` and `emit` can each be read from a harness param (§ Options from params).

#### Structured output

`output: { "schema": <JSON Schema> }` holds the model to a JSON Schema written
in the document, so the schema is part of the document's version hash. The
node behaves as a TypeScript `callModel` with an `output` schema does (spec
02): the model is sent the document's own schema as its response format, not
one derived from a validator, and its answer is JSON-parsed and checked
against it. An
answer that is not JSON or breaks the schema fails the node with
`model_parse_error`. The hydrator loads the schema with `z.fromJSONSchema` to
check answers; one it cannot load fails hydration with `INVALID_OUTPUT_SCHEMA`,
and `parseAndRunWorkflow` and `dynamicWorkflow` report it when they check the
document. An `acp-agent` node takes the same `output` (spec 27).

The node's output is the parsed value. A later node reads its fields from its
input or from `$steps.<id>` (spec 33):

```json
{
  "kind": "sequence",
  "id": "main",
  "steps": [
    {
      "kind": "callModel",
      "id": "triage",
      "instructions": "Read the ticket.",
      "output": {
        "schema": {
          "type": "object",
          "properties": { "title": { "type": "string" }, "urgent": { "type": "boolean" } },
          "required": ["title", "urgent"],
          "additionalProperties": false
        }
      }
    },
    { "kind": "compute", "id": "label", "expr": "$steps.triage.urgent ? 'now: ' & title : 'later'" }
  ]
}
```

### `invokeTool`

A single tool execution, independent of an LLM call.

```typescript
interface InvokeToolWorkflowNode {
  kind: 'invokeTool';
  id: string;
  toolName: string;
  args?: Record<string, unknown>;
}
```

| Field      | Required | Description                                         |
|------------|----------|-----------------------------------------------------|
| `toolName` | Yes      | Name of a tool in the hydration context registry.   |
| `args`     | No       | Arguments passed to the tool: JSON, with `{ "$expr" }` wherever a value is computed. |

The node hydrates to the `invokeTool` step (spec 02), so a call runs the same
gates as one written in TypeScript: the tool's `input` schema checks the args,
the `beforeToolCall` layers and the approver of a tool that declares
`needsApproval` may refuse it (`steering_denied`), and it is traced and
reported as `tool_call_started` / `tool_call_completed`. The node's output is
the tool's result. Like the step, it adds no item to the conversation.

`args` is plain JSON, with `{ "$expr": "<JSONata>" }` wherever a value is
computed from the node's input and `$steps` (spec 33), and `{ "$literal": … }`
around data to pass through untouched. One `{ "$expr" }` in place of the whole
object computes every argument. Any other object, `$`-prefixed keys included,
is data. The args are what the node writes: unlike `invokeTool()`, whose fixed
`args` are laid over the step's input, a node does not add its input. Write
`{ "$expr": "$" }` to pass the input, or `{ "$expr": "$merge([$, { … }])" }` to
lay args over it.

```json
{
  "kind": "invokeTool",
  "id": "file",
  "toolName": "file-ticket",
  "args": {
    "title": { "$expr": "$steps.triage.title" },
    "urgent": { "$expr": "urgent" },
    "source": "chat"
  }
}
```

A registered tool is also how a document runs host code in process, and how it
fails the flow: a tool that throws fails its node with `step_failed`, whose
`stepId` is the node and whose `cause` is the error the tool threw. Enclosing
`sequence` nodes wrap that in their own `step_failed`, so the host's error is
the innermost `cause`.

### `compute`

Computes a value from the input with an expression (spec 33). A leaf: depth 0.

```typescript
interface ComputeWorkflowNode {
  kind: 'compute';
  id: string;
  expr: Expression;
}
```

| Field  | Required | Description                                                         |
|--------|----------|---------------------------------------------------------------------|
| `expr` | Yes      | A JSONata expression, evaluated against the node's input (spec 33 § The Input). |

The output is the evaluated value written the way every node writes its output: a string stays a string, `null` becomes the empty string, and any other value becomes its JSON text. The next node reads that text back as structured data, so a chain of `compute` nodes — or a `loop` whose body is one — carries a state object from step to step:

```json
{
  "kind": "compute",
  "id": "step",
  "expr": "{ 'n': n - 1, 'sum': sum + n }"
}
```

Because output is text, a string result that is itself valid JSON (`"5"`, `"true"`) reads back as that JSON value at the next node. Keep strings inside an object to carry them as strings.

A result with no JSON form fails the node with `EXPRESSION_FAILED`: JSONata's "no value" (a path that matched nothing), or a function anywhere in the result. A `compute` node takes the shared `durable` and `replayKey` fields like any other node, runs once per item inside a dynamic `inParallel` `each`, and has its id suffixed like any other node inside a named `subflow`.

### `conditional`

Conditional routing: each route tests the input, and the first route whose test passes runs.

```typescript
type ConditionalRoute =
  | { match: string; target: WorkflowNode }
  | { expr: Expression; target: WorkflowNode };

interface ConditionalWorkflowNode {
  kind: 'conditional';
  id: string;
  routes: ConditionalRoute[];
  default?: WorkflowNode;
}
```

| Field     | Required | Description                                                        |
|-----------|----------|--------------------------------------------------------------------|
| `routes`  | Yes      | Ordered list of routes. First route whose test passes wins.        |
| `default` | No       | Fallback node when no route matches. Omitting produces a no-op.   |

Each route carries exactly one test; the schema rejects a route with both or neither. (A node whose `fromParams.route` names a function is routed by it instead, and its routes carry no test: § Options from params.)

- `match` — a case-insensitive substring of the input's text (§ Branch Route Hydration). Simple and model-friendly, for routing on prose.
- `expr` — an expression (spec 33) evaluated against the input. The route is taken if it gives `true` and skipped if it gives `false` or no value (a path that matches nothing); any other result fails with `EXPRESSION_FAILED`. Exact, for routing on structured state such as a counter or a `decide` node's answers.

Routes of both kinds may mix in one node; they are tried in order.

```json
{
  "kind": "conditional",
  "id": "pick",
  "routes": [
    { "expr": "n = 0", "target": { "kind": "callModel", "id": "done", "instructions": "Report the result." } },
    { "match": "urgent", "target": { "kind": "callModel", "id": "escalate", "instructions": "Escalate." } }
  ],
  "default": { "kind": "subflow", "id": "again", "ref": "countdown" }
}
```

An `expr` route is the natural base case for a recursive named workflow (§ Recursion): the route that stops the recursion tests the state the previous steps computed.

### `decide` and `routeSwitch`

Typed decisions and routing by them. The node shapes, validation rules, and
outputs are specified in `32-decide` ("JSON Workflow Nodes"). Unlike `conditional`,
`routeSwitch` routes on a model's answer rather than a substring of the input.
A `decide` node also takes `projection` and `emit`, as `callModel` does. A
`routeSwitch` whose `fromParams.on` names a function routes by it instead of by
a question: it takes `default`, needs no `uncertain`, and its `cases` are not
checked against a question (§ Options from params).

### `spawn`

Child execution with a fresh context boundary.

```typescript
interface SpawnWorkflowNode {
  kind: 'spawn';
  id: string;
  child: WorkflowNode;
  timeout?: number;
  layers?: string[];
  steers?: 'forward' | 'hold';
  subprocess?: string;
}
```

| Field     | Required | Description                                          |
|-----------|----------|------------------------------------------------------|
| `child`   | Yes      | The workflow subtree to execute in the child context. |
| `timeout` | No       | Maximum wall-clock milliseconds for the child.       |
| `subprocess` | No    | Named subprocess adapter the child runs through. The name is one `HydrationContext.resolveSubprocess` knows, resolved when the document hydrates (unknown name → `UNKNOWN_SUBPROCESS_REFERENCE`); it is the host's own code and needs no grant. A `runCode` node whose `execute` is a function (§ Options from params) resolves its `subprocess` the same way. Omit for the harness adapter. |
| `layers`  | No       | Context layer names resolved from the hydration context registry, same resolution as `withContext` (unknown name → `UNKNOWN_LAYER_REFERENCE`). Omit to inherit the parent's layers, which is the default `spawn` behaviour (spec 04); naming layers **replaces** the inherited set for the child. |
| `steers`  | No       | `'forward'` lets the child apply steers sent to the session while it runs; default `'hold'` keeps them queued until the child returns (spec 04). |

### `loop`

Repeating execution with termination.

```typescript
interface LoopWorkflowNode {
  kind: 'loop';
  id: string;
  body: WorkflowNode;
  until: UntilPredicate;
  maxIterations?: number | 'infinity';
  onError?: 'retry' | 'skip' | 'abort';
  maxHistorySize?: number;
  inbox?: { name: string; mode?: 'value' | 'queue' | 'topic'; capacity?: number; external?: boolean };
  parkTimeout?: number;
}
```

| Field           | Required | Description                                                                 |
|-----------------|----------|-----------------------------------------------------------------------------|
| `body`          | Yes      | The step tree executed each iteration.                                      |
| `until`         | Yes      | Termination predicate (see Until Predicates below).                         |
| `maxIterations` | No       | Hard cap: a positive integer, or `"infinity"` for none. Defaults to `1000`. |
| `onError`       | No       | What a failed body does: `retry` runs it again, `skip` keeps the last output, `abort` (the default) fails the loop. `fromParams.onError` decides per error. |
| `maxHistorySize` | No      | The most outputs kept for `until` (spec 05).                                |
| `inbox`         | No       | A channel of text, by name, read before the loop stops; a message runs it again (spec 05, 06). `mode` defaults to `queue`. |
| `parkTimeout`   | No       | How long, in ms, the loop waits on `inbox` before it stops.                 |

`fromParams.prepareNext` shapes the next iteration's input (§ Options from params). A body of several steps is a `sequence` node.

JSON cannot encode `Infinity`, so an uncapped loop spells it as the string literal `"infinity"` — exactly that spelling; any other string fails validation. The hydrator maps `"infinity"` to `Number.POSITIVE_INFINITY`, the same value the programmatic `loop({ maxIterations: Infinity })` takes (spec 05, Iteration Cap). An uncapped loop ends only through its `until` predicate, an error, or an aborted context, so pair it with a predicate that the body's output can actually satisfy (`outputContains`, `outputEquals`, `converged`, a `decide` node, …).

### `subflow`

Runs another workflow document as a single step — either inline or by name.

```typescript
interface SubflowWorkflowNode {
  kind: 'subflow';
  id: string;
  document?: SubflowDocument;   // a WorkflowDocument without `connections`
  ref?: string;
  input?: string;
}
```

| Field      | Required | Description                                                              |
|------------|----------|--------------------------------------------------------------------------|
| `document` | XOR      | Inline sub-workflow. Supply exactly one of `document` / `ref`.           |
| `ref`      | XOR      | Named sub-workflow resolved from `HydrationContext.workflows`.           |
| `input`    | No       | Literal input passed to the sub-workflow; defaults to the node's input.  |

Resolution is lazy: the target document resolves and hydrates on the node's first execution, memoized afterwards. A live `workflows` map may therefore gain entries after hydration and still satisfy refs. The hydrated sub-document's node ids are suffixed with `-<node id>` so two subflow nodes referencing the same named workflow trace with distinct step ids. A subflow document, inline or named, declares no `connections`: its nodes use the root document's. An inline one that does fails validation, and a named one fails with `CONNECTION_INVALID` when it resolves.

#### Recursion

Named refs may recurse: a workflow may reference itself, directly or through other named workflows. Recursion is how a JSON workflow expresses work whose shape depends on runtime data — a subflow node without a literal `input` passes its runtime input on, so the steps before a recursive call compute what that call receives, and a `conditional` (or any other routing node) picks the base case that stops it.

Each level of recursion is its own hydrated tree. The suffix applies to the whole sub-document, including the recursive subflow node itself, so each level's ids carry the id of the subflow node that called it — which already carries every suffix above it. Ids grow one segment per level (`body-top`, `body-rec-top`, `body-rec-rec-top`, …), so every level traces and replays under distinct step ids, and two recursive calls from different nodes (say, both paths of an `inParallel`) never share a tree. Levels hydrate lazily, so only as many exist as execution reaches.

Recursion is bounded by a depth limit, not banned. The **recursion depth** of a subflow call is the number of named-ref resolutions on its execution path, itself included; inline documents are finite JSON trees and add nothing. When a ref would resolve at a depth above `maxRecursionDepth` (default `100`, `Infinity` for none; see Hydration Context), the call throws `WORKFLOW_RECURSION_LIMIT` at execution time. A `maxRecursionDepth` that is neither a positive integer nor `Infinity` throws `INVALID_MAX_RECURSION_DEPTH` when a named ref first resolves. The limit is per path, so sibling nodes referencing the same workflow (diamond reuse) do not add to each other's depth.

`walkWorkflow`/`workflowGraph`/`workflowDepth` treat a `ref` as a leaf — static analysis does not see through named refs, so a recursive registry is still a finite graph to them.

## Until Predicates

Until predicates are JSON-serialisable termination conditions for `loop` nodes. They form a discriminated union on `kind` that mirrors the runtime `until.*` predicates.

```typescript
type UntilPredicate =
  | { kind: 'maxSteps';       n: number }
  | { kind: 'maxCost';        usd: number }
  | { kind: 'maxDuration';    duration: number }
  | { kind: 'noToolCalls' }
  | { kind: 'outputContains'; marker: string }
  | { kind: 'outputEquals';   sentinel: string }
  | { kind: 'never' }
  | { kind: 'converged';      threshold?: number }
  | { kind: 'expr';           expr: Expression }
  | { kind: 'param';          name: string }
  | { kind: 'any';            predicates: UntilPredicate[] }
  | { kind: 'all';            predicates: UntilPredicate[] }
  | DecideWorkflowNode;
```

### Predicate Reference

| Kind             | Fields          | Equivalent Runtime Predicate     | Description                                    |
|------------------|-----------------|----------------------------------|------------------------------------------------|
| `maxSteps`       | `n`             | `until.maxSteps(n)`              | Stop after `n` iterations.                     |
| `maxCost`        | `usd`           | `until.maxCost(usd)`            | Stop when cumulative cost exceeds threshold.   |
| `maxDuration`    | `duration`      | `until.maxDuration(duration)` | Stop after wall-clock time exceeds threshold.  |
| `noToolCalls`    | --              | `until.noToolCalls()`           | Stop when the LLM produces no tool calls.      |
| `never`          | --              | `until.never()`                 | Never stop; the loop ends on its cap, an error, or abort. |
| `outputContains` | `marker`        | `until.outputContains(marker)`  | Stop when output contains the marker string.   |
| `outputEquals`   | `sentinel`      | `until.outputEquals(sentinel)`  | Stop when output exactly equals the sentinel.  |
| `converged`      | `threshold?`    | `until.converged({threshold})`  | Stop when consecutive outputs are similar.     |
| `expr`           | `expr`          | --                              | Stop when `expr` (spec 33) gives `true` against the last output. |
| `param`          | `name`          | a custom `Until` function       | Ask the `Until` function the harness param `name` holds (§ Options from params). |
| `any`            | `predicates[]`  | `any(...predicates)`            | Stop when any child predicate fires.           |
| `all`            | `predicates[]`  | `all(...predicates)`            | Stop when all child predicates agree.          |
| `decide`         | a `decide` node | the `decide()` step itself      | Stop when the model answers yes.               |

### Decide Nodes as Predicates

A plain `decide` node (see `decide` and `routeSwitch`, spec 32) is a valid until predicate, alone or inside `any`/`all`. It carries no extra fields: the node itself is the decider. It must ask exactly one question, and that question must be boolean; the schema rejects any other decide node in predicate position (a refinement on the decide node schema), and the JS builders reject it with `INVALID_UNTIL_DECIDER`.

After each iteration the loop runs the decide step with the iteration's output as its input. A yes stops the loop, a no continues it, and a refusal continues it too. Each verdict's `reason` names the step, the question, the answer, and its probability. The decider asks afresh every iteration (spec 05, Ending a Loop with a Decision), so it never repeats a stale answer. With `"maxIterations": "infinity"`, a model that keeps refusing keeps the loop running until the context is aborted; a host that wants a backstop puts the decider in an `any` beside `maxSteps`.

A decide node in an until predicate is a node of the tree: `walkWorkflow` and `workflowGraph` list it as a child of its loop (after the body), so subflow and dynamic `each` id suffixing reach it, and its id should be unique like any other. It adds no depth: `workflowDepth` counts it as a leaf.

### `expr`

`expr` reads the loop's last output by the expression input rule (spec 33 § The Input) — a string is parsed as JSON when it parses — and evaluates the expression against it. `true` stops the loop; `false`, or no value (a path that matches nothing), runs another iteration. The stop verdict's `reason` is `expr gave true: <expr>`. A loop whose body computes a state object stops exactly when the state says so:

```json
{
  "kind": "loop",
  "id": "drain",
  "maxIterations": "infinity",
  "body": { "kind": "compute", "id": "step", "expr": "{ \"n\": n - 1 }" },
  "until": { "kind": "expr", "expr": "n = 0" }
}
```

An `expr` predicate is a predicate like any other: it nests inside `any` and `all` beside `maxSteps`, a `decide` node, or another `expr`, and validation compiles it wherever it sits, so a syntax error anywhere in the predicate tree fails the document with `WORKFLOW_VALIDATION_FAILED`.

An expression that fails at run time, or gives a value other than a boolean, raises `EXPRESSION_FAILED` (or `EXPRESSION_LIMIT_EXCEEDED`), and the loop fails with that error. It does not stop: a loop stops on a throwing predicate only when the error is not a `NoeticConfigError` (spec 05, Error Behavior), since a stop would hand back the last output as if the loop had finished.

### Schema

```typescript
const UntilPredicateSchema: z.ZodType<UntilPredicate> = z.lazy(() =>
  z.discriminatedUnion('kind', [
    z.object({ kind: z.literal('maxSteps'),       n: z.number().int().positive() }),
    z.object({ kind: z.literal('maxCost'),        usd: z.number().positive() }),
    z.object({ kind: z.literal('maxDuration'),    duration: z.number().int().positive() }),
    z.object({ kind: z.literal('noToolCalls') }),
    z.object({ kind: z.literal('never') }),
    z.object({ kind: z.literal('outputContains'), marker: z.string().min(1) }),
    z.object({ kind: z.literal('outputEquals'),   sentinel: z.string() }),
    z.object({ kind: z.literal('converged'),      threshold: z.number().min(0).max(1).optional() }),
```

## Hydration

Hydration converts a `WorkflowDocument` into a live `Step` tree that the interpreter can execute. The process is recursive, deterministic, and pure (no side effects).

### Hydration Context

```typescript
interface HydrationContext {
  tools: ReadonlyMap<string, Tool>;
  executeStep: ExecuteStepFn;
  layers?: ReadonlyMap<string, ContextLayer>;
  acpAgents?: ReadonlyMap<string, AcpAgent>;
  bindings?: Readonly<Record<string, string | ReadonlyArray<string>>>;
  uiLibraries?: ReadonlyMap<string, OutputCodec>;
  resolveSubprocess?: (ref: string) => SubprocessAdapter | undefined;
  workflows?: ReadonlyMap<string, WorkflowDocument>;
  maxRecursionDepth?: number;
  recursionDepth?: number;
  expressionLimits?: ExpressionLimits;
}
```

| Field                | Required | Description                                                              |
|----------------------|----------|--------------------------------------------------------------------------|
| `tools`              | Yes      | Registry mapping tool names to live `Tool` objects.                      |
| `executeStep`        | Yes      | The interpreter's `execute` function, threaded for recursive calls.      |
| `layers`             | No       | Named context layers for `withContext` nodes and `spawn.layers`.              |
| `acpAgents`          | No       | ACP agent adapters keyed by `agentId` (`claude-code`, `codex`, …). Open set. |
| `bindings`           | No       | Document connection name → harness connection name, when they differ (spec 35). Connection nodes resolve connections through the harness registry when they run. |
| `uiLibraries`        | No       | Output codecs for `callModel` nodes' `output` codec references.                |
| `resolveSubprocess`  | No       | Resolves the name a `runCode` or `spawn` node's `subprocess` gives. For a `runCode` node that carries code, a name it does not know is one of the harness's subprocess adapters, when `runCodeBounds` allows it (§ No In-Process Closures). A `spawn` node, and a `runCode` node whose `execute` is a function, resolve their `subprocess` through `resolveSubprocess` alone, when the document hydrates. |
| `runCodeBounds`      | No       | Internal: the `RunCodeGrant` that `runCode` nodes are held to when the host did not write the document. Set by `parseAndRunWorkflow` and `dynamicWorkflow`, dropped for named subflow refs; callers never set it (§ runCode). |
| `workflows`          | No       | Named sub-workflow documents that `subflow` nodes resolve via `ref`.     |
| `maxRecursionDepth`  | No       | Deepest allowed chain of named-ref resolutions on one path. Positive integer or `Infinity`; default `100`. |
| `recursionDepth`     | No       | Internal: named-ref resolutions above the node being hydrated. Threaded by the subflow hydrator; callers never set it. |
| `expressionLimits`   | No       | Bounds on each expression evaluation; see Constraints § Expression Limits. Unset fields use `DEFAULT_EXPRESSION_LIMITS`. |

### `hydrateWorkflow`

Top-level entry point. Validates the document, then hydrates the root node.

```typescript
function hydrateWorkflow(
  doc: WorkflowDocument,
  ctx: HydrationContext,
): Step<string, string>
```

A harness given the returned step as its `agentGraph` names its version by a hash of the document and the named workflows in `ctx.workflows`, stores both with each turn, and resumes a turn begun under an older document on that document, hydrated again with this `ctx` (`23-durable-execution` § Stored flows). A `workflow()` step does the same with its own options. The hydrator keeps what that takes; there is no API for it.

Hydration expects an already-validated document; schema validation and depth limits are enforced at parse time by `parseAndRunWorkflow`/`dynamicWorkflow` (`WORKFLOW_VALIDATION_FAILED`).

### `hydrateNode`

Recursive hydrator for a single node. Called by `hydrateWorkflow` and available for partial hydration.

```typescript
function hydrateNode(
  node: WorkflowNode,
  ctx: HydrationContext,
): Step<string, string>
```

### Node-to-Builder Mapping

Each node kind maps to a single existing builder:

| Node Kind   | Builder                   | Notes                                                  |
|-------------|---------------------------|--------------------------------------------------------|
| `callModel`       | `callModel({...})` | Tools resolved by name from `ctx.tools`.               |
| `invokeTool`      | `invokeTool({...})` | Tool resolved by name; throws `UNKNOWN_TOOL_REFERENCE`.|
| `compute`   | `runCode` wrapper | Evaluates `expr` against the read input; output written as text. |
| `conditional`    | `conditional({route: ...})` | Route function tests each route's `match` substring or `expr` expression. |
| `decide`    | `decide(...)`        | Questions pass through unchanged; output is the answers object. |
| `routeSwitch` | `routeSwitch(...)` | The key form, or the function form when `fromParams.on` names the function; cases, `default` and `uncertain` hydrate recursively. |
| `inParallel`      | `inParallel({...})` | `paths` becomes a static function. Merge via strategy, or via the function `fromParams.merge` names. |
| `spawn`     | `spawn({...})`            | Child hydrated recursively.                            |
| `withContext`   | `withContext({...})` | Layer names resolved from hydration context.           |
| `loop`      | `loop({...})`             | Until predicate hydrated to runtime `Until` function.  |
| `sequence`  | `runCode` + chaining | Steps piped sequentially via composed `execute` calls. |
| `schedule`     | `schedule({...})` | Maps directly to the `schedule()` builder.                |
| `subflow`   | `runCode` wrapper | Target document resolved lazily at first execution; sub-tree hydrated with suffixed ids. |

### Tool Resolution

The `type` of a `callModel.tools` client entry and `invokeTool.toolName` are resolved against `ctx.tools` at hydration time (connection entries resolve when the turn attaches them, § Tools). If a name is not found, hydration throws:

```typescript
{
  kind: 'UNKNOWN_TOOL_REFERENCE',
  message: `Tool "${name}" not found in registry. Available: ${[...ctx.tools.keys()].join(', ')}`,
}
```

This is a hard failure -- partial hydration with missing tools is not supported. The caller must ensure all referenced tools are registered before hydration.

### Branch Route Hydration

Branch `routes` are hydrated into a `route` function that tries each route in order. A `match` route tests its string as a case-insensitive substring against the input. An object input — or a string holding a JSON object or array, as a `sequence` passes a `decide` node's answers — is matched against its string values only, joined, never its keys. An `expr` route evaluates its expression against the input read by the expression input rule (spec 33) — a string is parsed as JSON when it parses — so it sees structured values, not text:

```typescript
route: (input, ctx) => {
  for (const route of routes) {
    if (passes(route, input)) {   // match: substring of routeText(input); expr: evaluate(...) === true
      return route.target;
    }
  }
  return defaultNode ?? null;
}
```

The input is read once per route call, not once per route. An `expr` that gives no value skips the route; one that gives a non-boolean fails with `EXPRESSION_FAILED` rather than skipping it. An `expr` that does not parse fails validation (`WORKFLOW_VALIDATION_FAILED`) before the workflow runs.

### Until Predicate Hydration

Each `UntilPredicate` node maps to a runtime `until.*` call, except a `decide` node, which hydrates to the decide step itself (through `hydrateNode`, so its `durable` and `replayKey` apply) and serves as the loop's `until` directly:

```typescript
function hydrateUntil(pred: UntilPredicate, ctx: HydrationContext): Until | StepDecide {
  switch (pred.kind) {
    case 'maxSteps':       return until.maxSteps(pred.n);
    case 'maxCost':        return until.maxCost(pred.usd);
    case 'maxDuration':    return until.maxDuration(pred.duration);
    case 'noToolCalls':    return until.noToolCalls();
    case 'never':          return until.never();
    case 'outputContains': return until.outputContains(pred.marker);
    case 'outputEquals':   return until.outputEquals(pred.sentinel);
    case 'converged':      return until.converged(pred.threshold ? { threshold: pred.threshold } : undefined);
    case 'expr':           return (snap) => ({ stop: passes(pred.expr, readInput(snap.lastOutput)) });  // require a boolean
    case 'param':          return (snap, run) => paramFunction(run.ctx, pred.name)(snap, run);          // read at each ask; must give a verdict
    case 'any':            return any(...pred.predicates.map((p) => hydrateUntil(p, ctx)));
    case 'all':            return all(...pred.predicates.map((p) => hydrateUntil(p, ctx)));
    case 'decide':         return hydrateNode(pred, ctx);
  }
}
```

### Depth Enforcement

Depth is measured by `workflowDepth` (structural nodes add +1 over their deepest child; leaves are 0) and enforced at parse time: `parseAndRunWorkflow` and `dynamicWorkflow` reject documents deeper than their `maxDepth` option (default `5`) with `WORKFLOW_VALIDATION_FAILED`. Depth does not see through `subflow` refs — a named sub-workflow's own depth is checked wherever that document is itself parsed. Recursion through refs is bounded at execution time by `maxRecursionDepth` (`WORKFLOW_RECURSION_LIMIT`), which caps the depth of any one path but not total fan-out: a workflow that references the next one several times multiplies execution combinatorially, up to the depth limit. Hosts that accept untrusted registries should keep `maxRecursionDepth` finite and cap registry size and per-document breadth accordingly.

## AgentHarness Integration

Two high-level integration points connect JSON workflows to the harness.

### `dynamicWorkflow` -- LLM-Generated Workflows

A `Step` that uses an LLM to generate a workflow document as structured output, validates it, hydrates it, and executes it within the same session.

```typescript
function dynamicWorkflow(opts: {
  id?: string;
  model: string;
  instructions: string;
  tools: Map<string, Tool>;
  maxRevisions?: number;
  maxDepth?: number;
  connections?: ConnectionAllowlist;
  acpAgents?: ReadonlyMap<string, AcpAgent>;
  acp?: AcpAllowlist;
  runCode?: RunCodeGrant;
  mcp?: McpAllowlist;
}): Step<string, string>
```

Execution flow:

1. Call the LLM with `WorkflowDocumentSchema` as the structured output schema.
2. Validate the response against `WorkflowDocumentSchema`.
3. If validation fails and revisions remain, feed the validation errors back to the LLM and retry from step 1.
4. If validation succeeds, hydrate the document via `hydrateWorkflow`.
5. Execute the hydrated `Step` tree with the current context.

```typescript
const planner = dynamicWorkflow({
  model: 'anthropic/claude-sonnet-4-20250514',
  instructions: `You are a workflow planner. Given a task description,
    generate a workflow document that accomplishes the task.
    Available tools: ${[...tools.keys()].join(', ')}`,
  tools: toolRegistry,
  maxRevisions: 3,
});

const result = await execute(planner, 'Analyze the codebase and fix all lint errors', ctx);
```

`maxRevisions` defaults to `2`. Each revision re-prompts the LLM with the previous attempt and the validation error. If all revisions are exhausted, execution throws `WORKFLOW_GENERATION_FAILED`.

### `parseAndRunWorkflow` -- Pre-Built Workflows

A standalone utility for executing a workflow document that already exists (loaded from a file, database, or API response).

```typescript
function parseAndRunWorkflow(opts: {
  json: unknown;
  harness: AgentHarnessContract;
  ctx: Context;
  tools: Tool[];
  input?: string;
  maxDepth?: number;
  layers?: ReadonlyMap<string, ContextLayer>;
  workflows?: ReadonlyMap<string, WorkflowDocument>;
  maxRecursionDepth?: number;
  connections?: ConnectionAllowlist;
  acpAgents?: ReadonlyMap<string, AcpAgent>;
  acp?: AcpAllowlist;
  runCode?: RunCodeGrant;
  mcp?: McpAllowlist;
}): Promise<string>
```

`maxRecursionDepth` (default `100`, `Infinity` for none) bounds recursion through the `workflows` registry; see `subflow` → Recursion. `dynamicWorkflow` takes no such option: its planner emits inline subflows only and has no registry to recurse through. The `workflow()` builder (spec 02) takes the same `workflows` + `maxRecursionDepth` pair, and a `workflow({ ref })` step counts its own ref as the first resolution.

This validates the document (schema + depth, throwing `WORKFLOW_VALIDATION_FAILED`), hydrates it, executes it via the harness inside a `workflow.run` trace span, and returns the final output:

```typescript
const result = await parseAndRunWorkflow({
  json: JSON.parse(workflowJson),
  harness,
  ctx,
  tools,
  input: userPrompt,
});
```

### Tools

A `callModel` node's `tools` entries are objects. Besides `{ "type": … }` (a registered client tool, or an `openrouter:*` server tool), two entries give the model a connection's tools — the same tools, under the same names, as the TypeScript step entries they hydrate to (spec 35 § Attaching connections):

```json
{ "kind": "callModel", "id": "triage", "instructions": "…", "tools": [
  { "connection": "linear", "ops": ["get_*"] },
  { "mcp": { "name": "docs", "type": "http", "url": "https://mcp.example.com/docs",
             "headers": [{ "name": "Authorization", "value": { "$secret": "docs.token" } }] } },
  { "type": "search" }
] }
```

- **`{ "connection", "ops"? }`** names a harness, turn or document connection and becomes `connectionTools(name, { ops })`: every tool of the connection, or only those whose operations all match the `ops` globs. It needs no `connections` manifest entry. A name no connection has fails with `CONNECTION_UNKNOWN` when the turn's tool set is built. Under a `connections` allowlist the name must be granted and each `ops` glob must lie inside a granted glob (`get_issue` and `get_*` inside `get_*`; `*` is not); without `ops` the pick takes exactly the granted operations. Anything else is `CONNECTION_NOT_ALLOWED`. `parseAndRunWorkflow` and `dynamicWorkflow` always hold a document to a `connections` allowlist — no option is `connections: {}` — so a `callModel` or `acp-agent` node gets exactly the tools it lists, and a node with no `tools` is offered each granted connection with exactly its granted operations plus the MCP servers the document's `connections` attach (its other tools are those of any step with no `tools`): with nothing granted, no connection. A pick of a server the document's own `connections` attach answers to `mcp`, not `connections`. `hydrateWorkflow` and `workflow()`, for documents the host wrote, apply no allowlist unless given one.
- **`{ "mcp": … }`** is an MCP server the step attaches, in ACP's `McpServer` shape as `mcp()` takes it: `{ "name", "type": "http" | "sse", "url", "headers"? }` or `{ "name", "command", "args"?, "env"? }`, like `tools: [mcp({ … })]`. Header and environment values are `$secret`s only; it takes no `cwd` and no `policy`, and the schema refuses any other key. The server must match an `mcp` grant (§ MCP servers), which supplies its secrets, its policy and the provider that connects it.

An `acp-agent` node takes the same two entries in its own `tools` (no `{ "type" }` entries): connections served to the agent with noetic as the MCP client, never handed to the agent's own MCP client (spec 27 § Tools). A stdio `{ "mcp" }` entry on an `acp-agent` node starts through its agent's `spawn`, where the agent runs: through the subprocess adapter the node names, when it names one. The `spawn` the host's `mcp.provider` is handed is already bound to the harness's subprocess adapters and the node's name, so a provider that calls `spawn(command)` and forwards nothing still starts the server there.

The same `{ "mcp" }` entry under the document's `connections`, keyed by its name, attaches the server for the whole document (spec 35 § JSON workflows):

```json
{ "version": 1,
  "connections": { "linear": { "mcp": { "name": "linear", "type": "http", "url": "https://mcp.linear.app/mcp",
    "headers": [{ "name": "Authorization", "value": { "$secret": "linear.token" } }] } } },
  "root": { "kind": "callModel", "id": "triage", "instructions": "…" } }
```

**A document run in the middle of a turn.** A step entry connects with the turn, before its tool set is built (spec 35 § Attaching connections). A document `parseAndRunWorkflow` or `dynamicWorkflow` hydrates from a running step did not exist then, so when the harness runs it, it attaches the document's entries — its nodes' and its `connections`' — to the turn (released when the turn ends) and adds their tools to the pool for that run only: the rest of the turn keeps the tool set it started with. A name the harness or turn already holds with a different provider or options — or, for an entry another `acp-agent` node attached, under another `subprocess` name — is `CONNECTION_NAME_TAKEN`.

### What a document may ask of an agent

`parseAndRunWorkflow` and `dynamicWorkflow` run documents the host did not write, so an `acp-agent` node gets only what the host grants, and a `runCode` node runs only where the host lets it. Three grants cover it, all checked at parse time (inline subflows included), before anything runs:

- **`acp`** (`AcpAllowlist`) — per agent id, the most a node may ask in `permissions`, `mode`, `model`, `subprocess`, `fs`, `shell`, `cwd`, `clientCapabilities` and `session` (§ ACP agents).
- **`runCode`** (`RunCodeGrant`) — the harness subprocess adapters a `runCode` node may name (§ runCode).
- **`mcp`** (`McpAllowlist`) — the MCP servers a document may attach as `{ "mcp" }` entries, in a node's `tools` or its `connections`, and the secrets their headers and environment may carry (§ MCP servers).

`acpAgents` is the registry of agents a node may name, not an allowlist: a node naming an agent outside it fails with `UNKNOWN_ACP_AGENT_REFERENCE`. Nothing else on the node is limited — `prompt` passes as written. Named subflow refs come from the host's own registry and are neither checked nor held to the grants: every registered workflow is one any document may invoke, run with the host's settings, so a host registers only workflows it would let an untrusted document run. A host that wrote the document itself runs it with `workflow()` (spec 02) or `hydrateWorkflow`, which check none of the `acp` or `runCode` limits.

#### ACP agents

```ts
parseAndRunWorkflow({
  json, harness, ctx, tools,
  acpAgents: createAcpAgentRegistry(claudeCode()),
  acp: {
    'claude-code': {
      permissions: { allow: [{ kind: 'read' }, { kind: 'edit', title: 'docs/' }] },
      cwd: '/srv/checkouts',
      clientCapabilities: { readTextFile: true, writeTextFile: true },
      modes: ['default'],
      session: { keepAlive: 'run' },
    },
  },
});
```

Each field of an `AcpAgentGrant` is a ceiling; an agent with no entry gets the narrowest default:

| Field | A node may | Default |
|-------|-----------|---------|
| `permissions.default` | set `default: "allow"` only when this is `'allow'`; `deny` and `cancel` always | deny only |
| `permissions.allow` | write an `allow` rule only when one of these covers it: the same `kind` when the grant sets one, and a `title` containing the grant's title (case-insensitive) when the grant sets one. `deny` rules are always accepted. | no `allow` rules |
| `permissions.persist` | set `persist` | no |
| `modes` | set `mode` to one of these. A mode can lift the agent's own permission prompts (`bypassPermissions`, `acceptEdits`), so none is granted by default. | no `mode` |
| `models` | set `model` to one of these. A model changes no permission, so any is allowed until the host lists some. | any `model` |
| `subprocess`, `fs`, `shell` | name one of these harness adapters in the node's field of the same name (`08-runtime` § Named Adapters). A name moves the agent's process, or the files and commands it reaches, to another host, so none is granted by default: a node runs on the harness's defaults. | no name |
| `cwd` | name an absolute, plain directory (no `.`, `..`, repeated or trailing `/`) that is this one or under it. A node without `cwd` runs in the grant's `cwd`, else the harness's as read at parse time — never as read when the step runs, which may have moved outside the grant. | the harness's working directory at parse time |
| `clientCapabilities` | turn on only the capabilities this turns on. A capability the node leaves out takes the grant's value, not the protocol client's default of on. | `{ readTextFile: true }` |
| `session.keepAlive` | set a `keepAlive` no longer than this: `'step'` or `'run'`. The document's session namespace ends with its run, so `'harness'` is never granted: it would only leak the agent process. | `'run'` |
| `session.load` | resume an agent session by id with `session.load` | no |

A document's sessions never join the host's. Each run of `parseAndRunWorkflow`, and each run of a `dynamicWorkflow` step, moves its nodes' `session.reuse` keys into a namespace of its own, so two nodes of one document still share a session, but no node can take over a session the host or another document opened — and the servers, cwd and capabilities it was opened with.

#### runCode

A `runCode` node's `subprocess` picks the host its code runs on, so a document may name a harness subprocess adapter only when the host's `runCode` grant lists it:

```ts
parseAndRunWorkflow({
  json, harness, ctx, tools,
  runCode: { subprocess: ['sandbox'] },
});
```

| Field | A node may | Default |
|-------|-----------|---------|
| `subprocess` | name one of these harness subprocess adapters (`08-runtime` § Named Adapters). A name moves the code to another host, so none is granted by default: a node runs on the harness's default. | no name |

A node naming an adapter the grant does not list fails validation with `CONNECTION_NOT_ALLOWED`. The refusal names the node, the name it asked for and the names the grant lists — never the harness's other adapters, which are not the document author's to learn. A granted name the harness lacks fails the step with `UNKNOWN_SUBPROCESS_REFERENCE`, which under a grant lists no names either. The hydrated node checks the grant again when it runs, so a node that reaches hydration unchecked is still refused. `dynamicWorkflow` shows its planner the granted names. `HydrationContext.resolveSubprocess` is the host's own code and comes first: a name it resolves needs no grant.

#### MCP servers

`parseAndRunWorkflow` and `dynamicWorkflow` accept an MCP server a document names — a `{ "mcp" }` entry in a node's `tools` or the document's `connections` — only when the host's `mcp` allowlist grants it, and check every server (inline subflows included) at parse time, before anything runs. Two different servers under one name — two nodes, or a node and the document's `connections` — are `CONNECTION_NAME_TAKEN` there too; the same server written the same way twice is one connection:

```ts
parseAndRunWorkflow({
  json, harness, ctx, tools,
  mcp: {
    urls: [{ url: 'https://mcp.example.com/*', secrets: { 'docs.token': 'Authorization' },
             policy: { deny: ['delete_*'] } }],
    commands: [{ command: 'npx', args: ['-y', '@acme/docs-mcp'], secrets: { 'docs.key': 'DOCS_KEY' } }],
    provider: mcp,   // from @noetic-tools/mcp: a granted server is the shape mcp() takes
  },
});
```

- **HTTP and SSE** servers are granted by a `url` pattern, `<scheme>://<host>[:<port>]<path>`, matched part by part so a `*` cannot stand for the `/`, `?`, `#` or `@` that would move a URL to another host. The scheme is `http` or `https`. The host matches case-insensitively and may start with `*.`, for one or more non-empty labels before the rest (not the rest itself, nor `.` + the rest). The rest must have at least two labels — `*.com` is invalid — and `*` anywhere else in the host is an invalid pattern (`CONNECTION_INVALID`). The port is a number or `*`, and when left out is the scheme's default. The path defaults to `/`, and in it `*` matches any run of characters. The query is not matched. Patterns are read through `URL` like the URLs they match, so `https://MCP.example.com:443/*` and `https://mcp.example.com/*` are the same pattern.
- **A server's URL** must be `http:` or `https:`, carry no user or password (`http://localhost:1@evil.example/` would otherwise match `http://localhost:*`), and be written exactly as `new URL(url).href` reads it back. The server is connected at the URL as written, so one that reads differently — a backslash, a tab, an uppercase host, a default port, a missing path — is refused rather than checked in one form and used in another.
- **Stdio** servers are granted by their exact command line: the same `command` and the same `args` in the same order (`args` defaults to none).
- **Header and environment values** come only from host secrets. A server names each header (case-insensitively) or variable at most once. Each must be `{ "$secret": "<name>" }` with a grant's `secrets` binding that name to that header (names compared case-insensitively) or variable (compared exactly); a literal value is refused. A server is accepted when any one grant matching it binds all its values, whatever the grant order; the first such grant is the server's grant. The secret is resolved through `environment.secrets` when the server connects and is scrubbed like any resolved secret; a document using a secret on a harness with no resolver fails at parse time with `CONNECTION_INVALID`.
- **Policy comes from the grant.** The connection entry gets its grant's `policy`; a document has no way to set one.
- **The host connects it.** `provider` builds the connection for the granted server — ACP's `McpServer` shape with its secrets resolved (`GrantedMcpServer`) — so `provider: mcp` is all it takes; core never imports `@noetic-tools/mcp`. A stdio server is the exact granted command, and the host decides where it runs. Without `provider`, a document that names a server fails with `CONNECTION_INVALID`. The same server under the same allowlist is always the same provider, so two nodes naming it share one connection.
- **No allowlist grants nothing.** An absent `mcp` refuses every server on both functions, as an absent `connections` grants no connection and an absent `acp` the narrowest agent settings: there is no trusted mode for a document. A host that trusts one passes the grants it wants.

A document asking for more than `acp`, `runCode` or `mcp` grants fails validation with `CONNECTION_NOT_ALLOWED`, naming the node (or the document's connections) and what it asked for. `dynamicWorkflow` feeds the refusal back to the planner like any validation error, and shows the planner the registered agent ids, each agent's limits, and only the granted servers.

## Options from params

A TypeScript step takes functions: a `model` getter, a `merge`, a loop's
`onError`. JSON cannot hold a function, so a node names one instead. The
function lives in the harness `params`, and the node's `fromParams` maps an
option to the param that holds it:

```json
{
  "kind": "callModel",
  "id": "ask",
  "instructions": "Answer the question.",
  "fromParams": { "model": "pickModel" }
}
```

```typescript
new AgentHarness({
  params: { pickModel: (ctx) => (ctx.depth > 0 ? 'small/model' : 'large/model') },
  // …
});
```

**Reading.** A param is looked up on the harness every time its option is
read, and a function is called then, with the arguments the option's
TypeScript function takes. Nothing is kept between reads: a param the host
swaps, or a function that answers differently, is seen at the next read. A
param that is not a function is the option's value, read the same way, so
`"fromParams": { "instructions": "systemPrompt" }` reads a string param.

**One or the other.** An option is written on the node or named in
`fromParams`, never both; both fails validation.

**Options.** Each node kind takes the options below. Every node also takes
`replayKey` (`(input, ctx) => string`), `emitItems` (the step's function form,
`(output, ctx) => string | Item | Item[] | undefined`), and `onStart` and
`onDone`, the hooks of its `emitItems` config (`(input, ctx)` and
`(output, ctx)`; each may be a generator that yields the item's events). The
last three must be functions.

| Node          | Option                | Called with                  | Gives                                      |
|---------------|-----------------------|------------------------------|--------------------------------------------|
| `callModel`   | `model`               | `(ctx)`                      | The model id.                              |
| `callModel`   | `instructions`        | `(ctx)`                      | The instructions.                          |
| `callModel`   | `tools`               | `(ctx)`                      | The step's tool entries.                   |
| `callModel`   | `emit`                | `(eventType, data, ctx)`     | `false` to drop the event.                 |
| `runCode`     | `execute`             | `(input, ctx)`               | The node's output. Runs in process; the node then carries no code and needs no subprocess adapter. A generator's yields are events of the item `emitItems` names, as in TypeScript. |
| `invokeTool`  | `args`                | `(input, ctx)`               | The tool's args.                           |
| `call`        | `args`                | `(input, ctx)`               | The operation's args.                      |
| `call`, `wait` | `connection`         | `(input, ctx)`               | The name of the connection to run on, checked against the manifest. |
| `wait`        | `filter`              | `(event, input, ctx)`        | `true` for the awaited event.              |
| `verify`      | `subject`             | `(input, ctx)`               | The name of the connection checked. The node then carries no `subject`. |
| `decide`      | `model`, `instructions` | `(ctx)`                    | As `callModel`.                            |
| `decide`      | `context`             | `(ctx)`                      | Extra state for the decision.              |
| `decide`      | `emit`                | `(eventType, data, ctx)`     | `false` to drop the event.                 |
| `routeSwitch` | `on`                  | `(answers, ctx)`             | The case to take. The node needs `default`; `uncertain` is optional. |
| `conditional` | `route`               | `(input, ctx, run)`          | The `id` of the target to take, or nothing for `default`. The routes carry no test. An id no target has fails with `UNKNOWN_ROUTE_TARGET`. |
| `inParallel`  | `merge`               | `(results, ctx)`             | The node's output. In `settle` mode `results` are the settled results, failures included. |
| `loop`        | `prepareNext`         | `(output, verdict, ctx)`     | The next iteration's input.                |
| `loop`        | `onError`             | `(error, ctx)`               | `'retry'`, `'skip'` or `'abort'`.          |
| `acp-agent`   | `prompt`, `instructions`, `cwd`, `mode`, `model`, `tools`, `content` | `(ctx)` | As the step's options. |
| `acp-agent`   | `onPermissionRequest` | `(request, ctx, info)`       | The permission outcome. Must be a function. |
| `acp-agent`   | `emit`                | `(eventType, data, ctx)`     | `false` to drop the event.                 |

A loop's `until` takes a function as the predicate
`{ "kind": "param", "name": "<param>" }`: an `Until`, called with
`(snapshot, run)` each time the loop asks (§ Until Predicates). It gives a
verdict, `{ stop: boolean, reason? }`; anything else fails the loop with
`INVALID_UNTIL_VERDICT`.

A `conditional`'s `route` function names its target by the id the document
wrote, also where the node sits in a subflow or an `each` template, whose
hydrated ids carry a suffix.

A `call`'s `args` function, in a document the host wrote, gives a step's args:
they may carry a `{ "$secret" }`, as `step.call({ args })` may. In a document
the host did not write they are a document's args, and a secret the document
did not write out is refused (`35-connections`).

**What the function is given.** `input` is the node's input as a JSON node
receives it: inside a `sequence`, the text of the node before it (an object
there arrives as its JSON text), so a function reads it with `JSON.parse`.

**Sync and async.** A function may return a promise wherever its TypeScript
option may. A loop's `prepareNext` and `onError`, `routeSwitch`'s `on`, an
`emit` filter and `replayKey` are synchronous in TypeScript; a param function
that gives a promise there fails with `PARAM_MUST_BE_SYNC` rather than being
used as a value. For `replayKey` that failure is treated as any `replayKey`
that throws: it is logged and the node runs without replay or recording
(`23a-step-level-resume`).

**Checking.** A document's param names are static, so they are checked before
anything runs: a harness refuses to start a run, or a turn, of a document that
reads a param it does not have (`UNKNOWN_PARAM_REFERENCE`), the named subflow
documents it reaches included. A param that holds a value where only a function
will do fails with `PARAM_NOT_A_FUNCTION` when it is read.

**Documents the host did not write.** A param can hold anything the host put
there, a secret included, so `parseAndRunWorkflow` and `dynamicWorkflow` let a
document read only the params named in their `params` option. With no
`params`, a document that reads any fails validation with `PARAM_NOT_ALLOWED`.
A grant is by param name: a granted function may be named at any option.

Such a document also cannot turn off `emit`, by value or by a granted
function, on a `callModel`, `decide` or `acp-agent` node: what it does stays
in the stream.

Some options decide what a node may reach, and the connection and ACP grants
are checked against the document, where a function's later answer cannot be
seen. Such a document may therefore not read them from a param at all, granted
or not (`PARAM_NOT_ALLOWED`): `tools` on `callModel`; `tools`, `cwd`, `mode`,
`model` and `onPermissionRequest` on `acp-agent`; `connection` on `call` and
`wait`; `subject` on `verify`.

`hydrateWorkflow` and `workflow()`, for documents the host wrote, apply
neither limit.

`fromParams` is part of the document, so naming a different param is a new
version. What the function does is not: a host that changes a param's
behaviour under a durable run answers for it, as with any TypeScript closure.

## Constraints

### No In-Process Closures

Programmatic `runCode` accepts an `execute` closure, which is not JSON-serialisable. The `runCode` node instead carries its body as a code STRING dispatched through a subprocess adapter — never eval'd in-process. A node with no `subprocess` runs through the harness's default (`ctx.subprocess`). A node that names one runs through the adapter `HydrationContext.resolveSubprocess` returns for the name, else the harness's subprocess adapter of that name (`08-runtime` § Named Adapters). In a document the host did not write — one run by `parseAndRunWorkflow` or `dynamicWorkflow` — a harness name must be one the host's `runCode` grant lists, and none is by default (§ runCode); `resolveSubprocess` is the host's own code and needs no grant. A name neither knows fails the step with `UNKNOWN_SUBPROCESS_REFERENCE`, whose message lists the harness's names only for a document the host wrote. In-process computation is a `compute` expression (spec 33), interpreted as data, or a function the host holds: one named by `fromParams.execute` on a `runCode` node that then carries no code (§ Options from params), or one registered as a tool. An adapter that reaches only a remote runner refuses the request with `SUBPROCESS_CANNOT_END_INPUT`, since the runner's frames carry no end of input (`08-runtime` § Request Dispatch).

### Static Lazy Fields Only

All fields in `WorkflowNode` are static JSON values. Fields that accept functions in the native builders are replaced with declarative equivalents (static arrays, substring matches, expressions) and, for every function a builder takes, a name in `fromParams` (§ Options from params). The exception is a function that returns steps, since a document's steps are its nodes: `inParallel`'s `paths` (`each` and `over` cover a data-dependent fan-out), `verify`'s `act` as a function of the subject (a list `subject` runs `act` once per subject, with `$item` bound), and a `conditional` `route` that builds the step it returns (the route function names one of the node's targets).

### Tool Names Resolved at Hydration Time

Tool references are strings, not `Tool` objects. Resolution happens once during hydration, not at each execution. If the tool registry changes after hydration, the hydrated step tree continues to reference the tools that were resolved at hydration time.

### Maximum Tree Depth

Tree depth is enforced at parse time to prevent unbounded recursion in LLM-generated workflows. The default limit is `5` levels of structural nesting, configurable via the `maxDepth` option on `parseAndRunWorkflow` and `dynamicWorkflow`. Depth does not see through `subflow` refs; recursion through them is bounded at execution time by `maxRecursionDepth` instead (see below).

### Unbounded Control Flow Is Opt-In

Two features let a workflow run without a static bound, and both are explicit opt-ins:

- **Uncapped loops.** `loop.maxIterations: "infinity"` removes the iteration cap; the loop ends only through its `until` predicate, an error, or an aborted context.
- **Recursive subflows.** Named refs may recurse; the path depth is capped by `maxRecursionDepth` (default `100`), which a host may raise to `Infinity`.

A host that runs untrusted documents keeps the defaults it wants enforced: the schema accepts `"infinity"`, so a host that must bound every loop rejects it before hydration, and a host that must bound recursion keeps `maxRecursionDepth` finite.

### Turing Completeness

With these opt-ins the document format is Turing complete. A `loop` with `"maxIterations": "infinity"` repeats without a static bound, a `compute` node (spec 33) carries a state object of unbounded integers from one iteration to the next, and an `expr` test — on a `conditional` route or as the loop's `{ "kind": "expr" }` until predicate — branches and halts on that state exactly. Together they simulate a two-counter machine; spec 33 § Worked Examples gives one. Recursive named subflows reach the same power by another road.

So whether a document halts cannot be decided before it runs, and the runtime does not try. Bounds come from the run's budgets instead: an aborted context, `maxCost` and `maxDuration` until predicates, `maxRecursionDepth`, and the per-evaluation expression limits (spec 33 § Limits). A host that runs untrusted documents sets the budgets it needs rather than relying on documents to be finite.

### Expression Limits

Every evaluation of a `compute` expression, a route's `expr`, or an `expr` until predicate runs under four bounds. A host sets them with `expressionLimits` on `parseAndRunWorkflow`, `dynamicWorkflow`, `workflow()`, or the `HydrationContext`; named and inline subflows inherit them.

```typescript
interface ExpressionLimits {
  timeout?: number; // default 1e3
  depth?: number;   // default 500
  length?: number;  // default 1e6
  steps?: number;   // default 1e6
}
```

| Limit     | Default | Bounds                                                                                       |
|-----------|---------|----------------------------------------------------------------------------------------------|
| `steps`   | `1e6`   | Sub-expressions evaluated, counting each repeat (each item of a path map, each function body run). Independent of the clock. |
| `depth`   | `500`   | How deep evaluation nests, counting each sub-expression and function call. A tail call does not nest: JSONata runs it in a loop. |
| `length`  | `1e6`   | Items in one sequence (JSONata's result list), including a range `[a..b]` and a sequence grown by `$append` or path mapping. |
| `timeout` | `1e3`   | Wall-clock milliseconds for one evaluation.                                                   |

- **Per evaluation.** Each run starts with a fresh clock, depth, and step count, so a loop that evaluates the same `expr` many times gets the full budget each time, and overlapping runs never share a count.
- **Each value is a positive integer or `Infinity`.** `Infinity` lifts that one bound; an unset field takes its default. Anything else — `0`, a negative number, a fraction, `NaN` — throws `INVALID_EXPRESSION_LIMITS` when the expression compiles at hydration.
- **Tripping a limit** throws `EXPRESSION_LIMIT_EXCEEDED` naming the limit and its value. It surfaces like `EXPRESSION_FAILED` (see Expression Failures).
- **Ranges have a fixed cap.** JSONata refuses a range of more than `1e7` items whatever `length` is, so `[1..1e8]` throws `EXPRESSION_LIMIT_EXCEEDED` even with every limit set to `Infinity`.
- **Checks run as each sub-expression starts.** `steps`, `depth`, and `timeout` are checked only there, so a single built-in call (a `$sort` of a large array, a costly regular expression) runs to its end before the next check.
- **`steps` is the bound that holds everywhere.** Endless tail recursion, such as `( $f := function($n){ $f($n + 1) }; $f(0) )`, never deepens, so only `steps` or `timeout` stops it. The timeout reads `Date.now()`, which Cloudflare Workers freeze during pure CPU work, so on Workers only `steps` stops it. A host that lifts `steps` on Workers leaves such an expression unbounded.
- **Deep input.** Evaluation never grows the JavaScript stack, but a built-in that walks deeply nested input (`$string`, the `**` descendant operator) recurses natively, outside the `depth` count. Overflowing the stack throws `EXPRESSION_LIMIT_EXCEEDED` rather than crashing.
- **Errors from built-ins.** A JavaScript error thrown inside a JSONata built-in during evaluation — such as the `TypeError` from `$base64encode` on a runtime without `Buffer` — is the expression's failure and throws `EXPRESSION_FAILED`.

## Plan-Memory Integration

The plan layer (spec 12, `plan()`) authors plans directly in this format: `PlanState.planTree` is a `WorkflowDocument`, and `PlanState.workflows` is a `Record<string, WorkflowDocument>` of named workflows the tree references via `subflow` nodes. The layer validates documents at authoring time (schema, depth, optional node-kind profile, ref slug syntax) and rejects dangling refs before requesting approval. Recursive refs are legal, matching the runtime; their depth is bounded when the plan executes.

On approval, the host feeds both pieces straight into this runtime:

```typescript
await parseAndRunWorkflow({
  json: state.planTree,
  workflows: new Map(Object.entries(state.workflows)),
  harness, ctx, tools, layers,
});
```

The split keeps the human-reviewed tree small — mechanics factor into named workflows the model authors and revises independently — while the whole plan stays one inspectable, portable JSON structure with stable node ids.

The hydrator prefixes an `EXPRESSION_FAILED` message with the node id. Where it surfaces depends on the node:

| Node                       | Surfaces as                                                                  |

| `conditional` route `expr` | The `NoeticConfigError` itself, thrown from the route function.               |
| `loop` until `expr`        | The `NoeticConfigError` itself, thrown from the loop: a config error from a predicate fails the loop instead of stopping it (spec 05). |

## Future Considerations

- **Custom until predicates via registered names.** A plugin could register a named predicate (e.g., `until.custom('myCheck')`) that the hydrator resolves from a predicate registry, similar to tool name resolution. This would allow domain-specific termination logic without extending the schema.
- **URI workflow references.** The `subflow` node resolves named refs from an in-memory registry; a URI form could fetch documents from remote workflow libraries, bounded by the same recursion limit.
- **Streaming hydration.** For very large workflows, hydrate nodes lazily as execution reaches them rather than building the entire `Step` tree upfront. This reduces memory pressure and startup latency.
- **Named context layer resolution for `withContext` nodes.** The current design uses string layer names, but the resolution mechanism is left to the `HydrationContext`. A standardised layer registry (analogous to the tool registry) would make `withContext` nodes portable across different harness configurations.
- **Workflow versioning and migration.** When `version` increments to `2`, a `migrateV1toV2` function would transform old documents automatically. The version field exists to enable this without breaking existing consumers.
