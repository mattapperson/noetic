# JSON Workflow Runtime

> **Depends On:** `01-step-type` (Step, Until), `02-step-variants` (callModel, invokeTool), `03-control-flow` (conditional, inParallel), `04-spawn` (spawn), `05-loop-and-until` (loop, until), `08-runtime` (AgentHarness), `33-expressions` (Expression)
> **Exports:** `WorkflowDocument`, `WorkflowNode`, `WorkflowDocumentSchema`, `WorkflowNodeSchema`, `UntilPredicateSchema`, `MergeStrategySchema`, `hydrateWorkflow`, `hydrateNode`, `dynamicWorkflow`, `parseAndRunWorkflow`

---

## Motivation

Step trees in noetic are built programmatically: TypeScript code calls builders like `callModel(...)`, `loop(...)`, `inParallel(...)` and wires them together at compile time. This works when the workflow shape is known ahead of time.

But many agent patterns need the shape to emerge at runtime:

1. **Plan-then-execute** -- An LLM generates a multi-step plan as structured output, then the harness executes it. The plan shape is not known until the model responds.
2. **Portable workflows** -- JSON documents can be stored in databases, passed between processes, shared across language boundaries, and audited after the fact. Closures cannot.
3. **User-authored workflows** -- End users or low-code tools define agent behavior as JSON configuration without writing TypeScript.
4. **Replay and inspection** -- A JSON workflow is a complete, inspectable record of what the agent intended to do, independent of execution state.

The JSON Workflow Runtime bridges these worlds: an LLM (or any producer) emits a `WorkflowDocument`, the runtime validates it, hydrates it into a native `Step` tree, and executes it with the same interpreter, context layers, and observability as hand-written compositions.

## Workflow Document Format

A workflow document is a versioned envelope around a single root node:

```typescript
interface WorkflowDocument {
  version: 1;
  root: WorkflowNode;
}
```

The `version` field enables forward-compatible parsing. Consumers reject documents with an unrecognised version rather than silently misinterpreting them.

```typescript
const WorkflowDocumentSchema = z.object({
  version: z.literal(1),
  root: WorkflowNodeSchema,
});
```

### Published JSON Schema

`WorkflowDocumentSchema` is the single source of truth. A standard JSON Schema (draft 2020-12) is serialised from it and published with the package so external tooling — editors, CI validators, and LLM planners — can validate documents without importing the runtime.

- The artifact is committed at `packages/core/schema/noetic-workflow.schema.json` and exposed at the `@noetic-tools/core/schema` export subpath. Its stable `$id` is `https://noetic.tools/schema/noetic-workflow.schema.json`, which resolves: a byte-identical copy is served by the web app from `packages/web/public/schema/noetic-workflow.schema.json`.
- It is generated by `bun run gen:schema` (`scripts/generate-workflow-schema.ts`), which calls `z.toJSONSchema(WorkflowDocumentSchema, { target: 'draft-2020-12' })` and writes both the published core artifact and the hosted web copy. The recursive types — `WorkflowNode`, `UntilPredicate`, and `Expression` (spec 33), plus the `JsonValue` that an expression's `quote` holds — are emitted as named `$defs`; every other subschema is inlined.
- A drift-gate test re-serialises the schema and asserts both committed copies are byte-for-byte current, and that the published variants cover exactly the runtime node and predicate kinds. CI fails if `gen:schema` was not re-run after a schema change.

Authoring documents by hand or reviewing LLM-generated ones, reference the schema with a `$schema` key so editors surface autocompletion and inline errors:

```jsonc
{
  "$schema": "https://noetic.tools/schema/noetic-workflow.schema.json",
  "version": 1,
  "root": { "kind": "callModel", "id": "answer", "instructions": "..." }
}
```

## WorkflowNode Union

`WorkflowNode` is a discriminated union on `kind`. Each variant maps to an existing `Step` builder. All nodes share three fields: a required `id`, an optional boolean `durable` that the hydrator copies onto the built step, and an optional declarative `replayKey` (§ Replay keys) that the hydrator turns into the step's `replayKey` function. `durable: false` keeps the node out of the step ledger, so a resumed run re-runs it instead of replaying its recorded output (`23a-step-level-resume` § Identity). The `acp-agent` node kind is specified in `27-acp-agent-steps`.

```typescript
type WorkflowNode =
  | CallModelWorkflowNode
  | InvokeToolWorkflowNode
  | RunCodeWorkflowNode
  | ComputeWorkflowNode
  | ConditionalWorkflowNode
  | DecideWorkflowNode
  | RouteSwitchWorkflowNode
  | InParallelWorkflowNode
  | SpawnWorkflowNode
  | WithContextWorkflowNode
  | LoopWorkflowNode
  | SequenceWorkflowNode
  | ScheduleWorkflowNode
  | SubflowWorkflowNode
  | AcpAgentWorkflowNode;
```

### Replay keys

A programmatic step's `replayKey` is a function (`23a-step-level-resume` § Identity); a JSON node cannot carry one. It names instead which part of its input identifies the work, and the hydrator builds the function:

```typescript
type WorkflowReplayKey =
  | true                    // key on the whole input
  | { from: string[] };     // key on these top-level properties of the input, parsed as JSON
```

`from` reads each property the way an `inParallel` node's `over` reads its array: the input is parsed as JSON and the named top-level key is looked up. A replay key is a list of names rather than an expression (spec 33), so the ledger key stays readable and cannot fail to evaluate. A missing property keys as `null`.

The built key is `<node id>:<hash>`, where the hash covers the whole input (`true`) or the JSON list of the selected values (`from`), via `hashString`. Prefixing the node id keeps two different nodes that read the same input — a `grade` and a `summarize` of one batch — from sharing a ledger entry and discarding each other's on every resume. Nodes that share an id share entries, which is how one worker leaf written into several `inParallel` paths finds its batch's answer whichever path runs it:

```json
{
  "kind": "inParallel", "id": "pool", "mode": "all", "durable": false, "merge": "concat",
  "paths": [
    { "kind": "sequence", "id": "worker-a", "durable": false, "steps": [
      { "kind": "runCode", "id": "worker-a-pick", "durable": false, "execute": "…", "subprocess": "sandbox" },
      { "kind": "runCode", "id": "grade", "replayKey": true, "execute": "…", "subprocess": "sandbox" }
    ] },
    { "kind": "sequence", "id": "worker-b", "durable": false, "steps": [
      { "kind": "runCode", "id": "worker-b-pick", "durable": false, "execute": "…", "subprocess": "sandbox" },
      { "kind": "runCode", "id": "grade", "replayKey": true, "execute": "…", "subprocess": "sandbox" }
    ] }
  ]
}
```

`from` on an input that is not a JSON object makes the key function throw `INVALID_REPLAY_KEY_INPUT`; the interpreter treats a throwing `replayKey` as it does for code (warn, run the step without replay or recording), so the node still runs. `replayKey` is ignored on a node that is also `durable: false`.

Inside a dynamic `inParallel` (`each`), the hydrator suffixes every template node id with the item index, and replay matches `stepId` as well as the key. A keyed node there therefore replays only when its item lands at the same index — content keys do not survive a reordered `each` input.

### `compute`

Computes a value from the input with an expression (spec 33). A leaf: depth 0.

```typescript
interface ComputeWorkflowNode {
  kind: 'compute';
  id: string;
  expr: Expression;
}
```

| Field  | Required | Description                                                         |
|--------|----------|---------------------------------------------------------------------|
| `expr` | Yes      | The expression, evaluated against the node's input (spec 33 § The Input). |

The output is the evaluated value written the way every node writes its output: a string stays a string, `null` becomes the empty string, and any other value becomes its JSON text. The next node reads that text back as structured data, so a chain of `compute` nodes — or a `loop` whose body is one — carries a state object from step to step:

```json
{
  "kind": "compute",
  "id": "step",
  "expr": {
    "object": {
      "counter": { "-": [{ "get": "counter" }, 1] },
      "sum": { "+": [{ "get": "sum" }, { "get": "counter" }] }
    }
  }
}
```

Because output is text, a string result that is itself valid JSON (`"5"`, `"true"`) reads back as that JSON value at the next node. Keep strings inside an object to carry them as strings.

### `conditional`

Conditional routing: each route tests the input, and the first route whose test passes runs.

```typescript
type ConditionalRoute =
  | { match: string; target: WorkflowNode }
  | { when: Expression; target: WorkflowNode };

interface ConditionalWorkflowNode {
  kind: 'conditional';
  id: string;
  routes: ConditionalRoute[];
  default?: WorkflowNode;
}
```

| Field     | Required | Description                                                        |
|-----------|----------|--------------------------------------------------------------------|
| `routes`  | Yes      | Ordered list of routes. First route whose test passes wins.        |
| `default` | No       | Fallback node when no route matches. Omitting produces a no-op.   |

Each route carries exactly one test; the schema rejects a route with both or neither:

- `match` — a case-insensitive substring of the input's text (§ Branch Route Hydration). Simple and model-friendly, for routing on prose.
- `when` — an expression (spec 33) evaluated against the input. The route is taken when it evaluates to `true`, skipped when `false`; any other result fails with `EXPRESSION_FAILED`. Exact, for routing on structured state.

Routes of both kinds may mix in one node; they are tried in order.

### `decide` and `routeSwitch`

Typed decisions and routing by them. The node shapes, validation rules, and
outputs are specified in `32-decide` ("JSON Workflow Nodes"). Unlike `conditional`,
`routeSwitch` routes on a model's answer rather than a substring of the input.

### `loop`

Repeating execution with termination.

```typescript
interface LoopWorkflowNode {
  kind: 'loop';
  id: string;
  body: WorkflowNode;
  until: UntilPredicate;
  maxIterations?: number | 'infinity';
}
```

| Field           | Required | Description                                                                 |
|-----------------|----------|-----------------------------------------------------------------------------|
| `body`          | Yes      | The step tree executed each iteration.                                      |
| `until`         | Yes      | Termination predicate (see Until Predicates below).                         |
| `maxIterations` | No       | Hard cap: a positive integer, or `"infinity"` for none. Defaults to `1000`. |

JSON cannot encode `Infinity`, so an uncapped loop spells it as the string literal `"infinity"` — exactly that spelling; any other string fails validation. The hydrator maps `"infinity"` to `Number.POSITIVE_INFINITY`, the same value the programmatic `loop({ maxIterations: Infinity })` takes (spec 05, Iteration Cap). An uncapped loop ends only through its `until` predicate, an error, or an aborted context, so pair it with a predicate that the body's output can actually satisfy (`outputContains`, `outputEquals`, `converged`, a `decide` node, …).

### `subflow`

Runs another workflow document as a single step — either inline or by name.

```typescript
interface SubflowWorkflowNode {
  kind: 'subflow';
  id: string;
  document?: WorkflowDocument;
  ref?: string;
  input?: string;
}
```

| Field      | Required | Description                                                              |
|------------|----------|--------------------------------------------------------------------------|
| `document` | XOR      | Inline sub-workflow. Supply exactly one of `document` / `ref`.           |
| `ref`      | XOR      | Named sub-workflow resolved from `HydrationContext.workflows`.           |
| `input`    | No       | Literal input passed to the sub-workflow; defaults to the node's input.  |

Resolution is lazy: the target document resolves and hydrates on the node's first execution, memoized afterwards. A live `workflows` map may therefore gain entries after hydration and still satisfy refs. The hydrated sub-document's node ids are suffixed with `-<node id>` so two subflow nodes referencing the same named workflow trace with distinct step ids.

#### Recursion

Named refs may recurse: a workflow may reference itself, directly or through other named workflows. Recursion is how a JSON workflow expresses work whose shape depends on runtime data — a subflow node without a literal `input` passes its runtime input on, so the steps before a recursive call compute what that call receives, and a `conditional` (or any other routing node) picks the base case that stops it.

Each level of recursion is its own hydrated tree. The suffix applies to the whole sub-document, including the recursive subflow node itself, so each level's ids carry the id of the subflow node that called it — which already carries every suffix above it. Ids grow one segment per level (`body-top`, `body-rec-top`, `body-rec-rec-top`, …), so every level traces and replays under distinct step ids, and two recursive calls from different nodes (say, both paths of an `inParallel`) never share a tree. Levels hydrate lazily, so only as many exist as execution reaches.

Recursion is bounded by a depth limit, not banned. The **recursion depth** of a subflow call is the number of named-ref resolutions on its execution path, itself included; inline documents are finite JSON trees and add nothing. When a ref would resolve at a depth above `maxRecursionDepth` (default `100`, `Infinity` for none; see Hydration Context), the call throws `WORKFLOW_RECURSION_LIMIT` at execution time. A `maxRecursionDepth` that is neither a positive integer nor `Infinity` throws `INVALID_MAX_RECURSION_DEPTH` when a named ref first resolves. The limit is per path, so sibling nodes referencing the same workflow (diamond reuse) do not add to each other's depth.

`walkWorkflow`/`workflowGraph`/`workflowDepth` treat a `ref` as a leaf — static analysis does not see through named refs, so a recursive registry is still a finite graph to them.

## Until Predicates

Until predicates are JSON-serialisable termination conditions for `loop` nodes. They form a discriminated union on `kind` that mirrors the runtime `until.*` predicates.

```typescript
type UntilPredicate =
  | { kind: 'when';           test: Expression }
  | { kind: 'maxSteps';       n: number }
  | { kind: 'maxCost';        usd: number }
  | { kind: 'maxDuration';    duration: number }
  | { kind: 'noToolCalls' }
  | { kind: 'outputContains'; marker: string }
  | { kind: 'outputEquals';   sentinel: string }
  | { kind: 'converged';      threshold?: number }
  | { kind: 'any';            predicates: UntilPredicate[] }
  | { kind: 'all';            predicates: UntilPredicate[] }
  | DecideWorkflowNode;
```

### Predicate Reference

| Kind             | Fields          | Equivalent Runtime Predicate     | Description                                    |
|------------------|-----------------|----------------------------------|------------------------------------------------|
| `maxSteps`       | `n`             | `until.maxSteps(n)`              | Stop after `n` iterations.                     |
| `maxCost`        | `usd`           | `until.maxCost(usd)`            | Stop when cumulative cost exceeds threshold.   |
| `maxDuration`    | `duration`      | `until.maxDuration(duration)` | Stop after wall-clock time exceeds threshold.  |
| `noToolCalls`    | --              | `until.noToolCalls()`           | Stop when the LLM produces no tool calls.      |
| `outputContains` | `marker`        | `until.outputContains(marker)`  | Stop when output contains the marker string.   |
| `outputEquals`   | `sentinel`      | `until.outputEquals(sentinel)`  | Stop when output exactly equals the sentinel.  |
| `converged`      | `threshold?`    | `until.converged({threshold})`  | Stop when consecutive outputs are similar.     |
| `when`           | `test`          | --                              | Stop when `test` (spec 33) evaluates to `true` against the last output. |
| `any`            | `predicates[]`  | `any(...predicates)`            | Stop when any child predicate fires.           |
| `all`            | `predicates[]`  | `all(...predicates)`            | Stop when all child predicates agree.          |
| `decide`         | a `decide` node | the `decide()` step itself      | Stop when the model answers yes.               |

### Decide Nodes as Predicates

A plain `decide` node (see `decide` and `routeSwitch`, spec 32) is a valid until predicate, alone or inside `any`/`all`. It carries no extra fields: the node itself is the decider. It must ask exactly one question, and that question must be boolean; the schema rejects any other decide node in predicate position (a refinement on the decide node schema), and the JS builders reject it with `INVALID_UNTIL_DECIDER`.

After each iteration the loop runs the decide step with the iteration's output as its input. A yes stops the loop, a no continues it, and a refusal continues it too. Each verdict's `reason` names the step, the question, the answer, and its probability. The decider asks afresh every iteration (spec 05, Ending a Loop with a Decision), so it never repeats a stale answer. With `"maxIterations": "infinity"`, a model that keeps refusing keeps the loop running until the context is aborted; a host that wants a backstop puts the decider in an `any` beside `maxSteps`.

A decide node in an until predicate is a node of the tree: `walkWorkflow` and `workflowGraph` list it as a child of its loop (after the body), so subflow and dynamic `each` id suffixing reach it, and its id should be unique like any other. It adds no depth: `workflowDepth` counts it as a leaf.

### `when`

`when` reads the loop's last output by the expression input rule (spec 33 § The Input) — a string is parsed as JSON when it parses — and evaluates `test` against it. `true` stops the loop, `false` runs another iteration. A loop whose body computes a state object stops exactly when the state says so:

```json
{
  "kind": "loop",
  "id": "drain",
  "maxIterations": 100,
  "body": { "kind": "compute", "id": "step", "expr": { "...": "..." } },
  "until": { "kind": "when", "test": { "==": [{ "get": "counter" }, 0] } }
}
```

A `test` that fails, or gives a value other than a boolean, raises `EXPRESSION_FAILED`; a loop treats a throwing predicate as a stop (spec 05), so the loop ends and the error message becomes the recorded verdict's reason. `maxIterations` still bounds the loop.

### Schema

```typescript
const UntilPredicateSchema: z.ZodType<UntilPredicate> = z.lazy(() =>
  z.discriminatedUnion('kind', [
    z.object({ kind: z.literal('maxSteps'),       n: z.number().int().positive() }),
    z.object({ kind: z.literal('maxCost'),        usd: z.number().positive() }),
    z.object({ kind: z.literal('maxDuration'),    duration: z.number().int().positive() }),
    z.object({ kind: z.literal('noToolCalls') }),
    z.object({ kind: z.literal('outputContains'), marker: z.string().min(1) }),
    z.object({ kind: z.literal('outputEquals'),   sentinel: z.string() }),
    z.object({ kind: z.literal('converged'),      threshold: z.number().min(0).max(1).optional() }),
    z.object({ kind: z.literal('when'),           test: ExpressionSchema }),
    z.object({ kind: z.literal('any'),            predicates: z.array(UntilPredicateSchema).min(1) }),
    z.object({ kind: z.literal('all'),            predicates: z.array(UntilPredicateSchema).min(1) }),
    DecideNodeSchema.refine(oneBooleanQuestion),
  ])
);
```

## Merge Strategies

`inParallel` nodes use a `MergeStrategy` to combine results from parallel paths. This replaces the closure-based `MergeFn<O>` from the native `inParallel()` builder with a named enum.

```typescript
type MergeStrategy = 'last' | 'first' | 'concat';
```

| Strategy | Behavior                                                                 |
|----------|--------------------------------------------------------------------------|
| `last`   | Return the result of the last-completed path. This is the default.       |
| `first`  | Return the result of the first-completed path. Equivalent to `race`.     |
| `concat` | Concatenate all results into a single string (joined with newlines).     |

```typescript
const MergeStrategySchema = z.enum(['last', 'first', 'concat']);
```

## Hydration

Hydration converts a `WorkflowDocument` into a live `Step` tree that the interpreter can execute. The process is recursive, deterministic, and pure (no side effects).

### Hydration Context

```typescript
interface HydrationContext {
  tools: ReadonlyMap<string, Tool>;
  executeStep: ExecuteStepFn;
  layers?: ReadonlyMap<string, ContextLayer>;
  acpAgents?: ReadonlyMap<string, AcpAgent>;
  uiLibraries?: ReadonlyMap<string, OutputCodec>;
  resolveSubprocess?: (ref: string) => SubprocessAdapter | undefined;
  workflows?: ReadonlyMap<string, WorkflowDocument>;
  maxRecursionDepth?: number;
  recursionDepth?: number;
}
```

| Field                | Required | Description                                                              |
|----------------------|----------|--------------------------------------------------------------------------|
| `tools`              | Yes      | Registry mapping tool names to live `Tool` objects.                      |
| `executeStep`        | Yes      | The interpreter's `execute` function, threaded for recursive calls.      |
| `layers`             | No       | Named context layers for `withContext` nodes and `spawn.layers`.              |
| `acpAgents`          | No       | ACP agent adapters keyed by `agentId` (`claude-code`, `codex`, …). Open set. |
| `uiLibraries`        | No       | Output codecs for `callModel` nodes' `output` codec references.                |
| `resolveSubprocess`  | No       | Resolves a named subprocess adapter ref on a `runCode` node.                 |
| `workflows`          | No       | Named sub-workflow documents that `subflow` nodes resolve via `ref`.     |
| `maxRecursionDepth`  | No       | Deepest allowed chain of named-ref resolutions on one path. Positive integer or `Infinity`; default `100`. |
| `recursionDepth`     | No       | Internal: named-ref resolutions above the node being hydrated. Threaded by the subflow hydrator; callers never set it. |

### `hydrateWorkflow`

Top-level entry point. Validates the document, then hydrates the root node.

```typescript
function hydrateWorkflow(
  doc: WorkflowDocument,
  ctx: HydrationContext,
): Step<string, string>
```

Hydration expects an already-validated document; schema validation and depth limits are enforced at parse time by `parseAndRunWorkflow`/`dynamicWorkflow` (`WORKFLOW_VALIDATION_FAILED`).

### `hydrateNode`

Recursive hydrator for a single node. Called by `hydrateWorkflow` and available for partial hydration.

```typescript
function hydrateNode(
  node: WorkflowNode,

```

### Node-to-Builder Mapping

Each node kind maps to a single existing builder:

| Node Kind   | Builder                   | Notes                                                  |
|-------------|---------------------------|--------------------------------------------------------|
| `callModel`       | `callModel({...})` | Tools resolved by name from `ctx.tools`.               |
| `invokeTool`      | `invokeTool({...})` | Tool resolved by name; throws `UNKNOWN_TOOL_REFERENCE`.|
| `compute`   | `runCode` wrapper | Evaluates `expr` against the read input; output written as text. |
| `conditional`    | `conditional({route: ...})` | Route function tests each route's `match` substring or `when` expression. |
| `decide`    | `decide(...)`        | Questions pass through unchanged; output is the answers object. |
| `routeSwitch` | `routeSwitch(...)` | Key form only; cases and `uncertain` hydrate recursively. |
| `inParallel`      | `inParallel({...})` | `paths` becomes a static function. Merge via strategy. |
| `spawn`     | `spawn({...})`            | Child hydrated recursively.                            |
| `withContext`   | `withContext({...})` | Layer names resolved from hydration context.           |
| `loop`      | `loop({...})`             | Until predicate hydrated to runtime `Until` function.  |
| `sequence`  | `runCode` + chaining | Steps piped sequentially via composed `execute` calls. |
| `schedule`     | `schedule({...})` | Maps directly to the `schedule()` builder.                |
| `subflow`   | `runCode` wrapper | Target document resolved lazily at first execution; sub-tree hydrated with suffixed ids. |

### Tool Resolution

Tool names in `callModel.tools` and `invokeTool.toolName` are resolved against `ctx.tools` at hydration time. If a name is not found, hydration throws:

```typescript
{
  kind: 'UNKNOWN_TOOL_REFERENCE',
  message: `Tool "${name}" not found in registry. Available: ${[...ctx.tools.keys()].join(', ')}`,
}
```

This is a hard failure -- partial hydration with missing tools is not supported. The caller must ensure all referenced tools are registered before hydration.

### Branch Route Hydration

Branch `routes` are hydrated into a `route` function that tries each route in order. A `match` route tests its string as a case-insensitive substring against the input. An object input — or a string holding a JSON object or array, as a `sequence` passes a `decide` node's answers — is matched against its string values only, joined, never its keys. A `when` route evaluates its expression against the input read by the expression input rule (spec 33):

```typescript
route: (input, ctx) => {
  for (const route of routes) {
    if (passes(route, input)) {   // match: substring of routeText(input); when: evaluate(...) === true
      return route.target;
    }
  }
  return defaultNode ?? null;
}
```

The input is read once per route call, not once per route, and a `when` that gives a non-boolean fails with `EXPRESSION_FAILED` rather than skipping the route.

### Until Predicate Hydration

Each `UntilPredicate` node maps to a runtime `until.*` call, except a `decide` node, which hydrates to the decide step itself (through `hydrateNode`, so its `durable` and `replayKey` apply) and serves as the loop's `until` directly:

```typescript
function hydrateUntil(pred: UntilPredicate, ctx: HydrationContext): Until | StepDecide {
  switch (pred.kind) {
    case 'maxSteps':       return until.maxSteps(pred.n);
    case 'maxCost':        return until.maxCost(pred.usd);
    case 'maxDuration':    return until.maxDuration(pred.duration);
    case 'noToolCalls':    return until.noToolCalls();
    case 'outputContains': return until.outputContains(pred.marker);
    case 'outputEquals':   return until.outputEquals(pred.sentinel);
    case 'converged':      return until.converged(pred.threshold ? { threshold: pred.threshold } : undefined);
    case 'when':           return (snap) => ({ stop: test(pred.test, snap.lastOutput) });  // test: evaluate, require a boolean
    case 'any':            return any(...pred.predicates.map((p) => hydrateUntil(p, ctx)));
    case 'all':            return all(...pred.predicates.map((p) => hydrateUntil(p, ctx)));
    case 'decide':         return hydrateNode(pred, ctx);
  }
}
```

### Depth Enforcement

Depth is measured by `workflowDepth` (structural nodes add +1 over their deepest child; leaves are 0) and enforced at parse time: `parseAndRunWorkflow` and `dynamicWorkflow` reject documents deeper than their `maxDepth` option (default `5`) with `WORKFLOW_VALIDATION_FAILED`. Depth does not see through `subflow` refs — a named sub-workflow's own depth is checked wherever that document is itself parsed. Recursion through refs is bounded at execution time by `maxRecursionDepth` (`WORKFLOW_RECURSION_LIMIT`), which caps the depth of any one path but not total fan-out: a workflow that references the next one several times multiplies execution combinatorially, up to the depth limit. Hosts that accept untrusted registries should keep `maxRecursionDepth` finite and cap registry size and per-document breadth accordingly.

## AgentHarness Integration

Two high-level integration points connect JSON workflows to the harness.

### `dynamicWorkflow` -- LLM-Generated Workflows

A `Step` that uses an LLM to generate a workflow document as structured output, validates it, hydrates it, and executes it within the same session.

```typescript
function dynamicWorkflow(opts: {
  id?: string;
  model: string;
  instructions: string;
  tools: Map<string, Tool>;
  maxRevisions?: number;
  maxDepth?: number;
}): Step<string, string>
```

Execution flow:

1. Call the LLM with `WorkflowDocumentSchema` as the structured output schema.
2. Validate the response against `WorkflowDocumentSchema`.
3. If validation fails and revisions remain, feed the validation errors back to the LLM and retry from step 1.
4. If validation succeeds, hydrate the document via `hydrateWorkflow`.
5. Execute the hydrated `Step` tree with the current context.

```typescript
const planner = dynamicWorkflow({
  model: 'anthropic/claude-sonnet-4-20250514',
  instructions: `You are a workflow planner. Given a task description,
    generate a workflow document that accomplishes the task.
    Available tools: ${[...tools.keys()].join(', ')}`,
  tools: toolRegistry,
  maxRevisions: 3,
});

const result = await execute(planner, 'Analyze the codebase and fix all lint errors', ctx);
```

`maxRevisions` defaults to `2`. Each revision re-prompts the LLM with the previous attempt and the validation error. If all revisions are exhausted, execution throws `WORKFLOW_GENERATION_FAILED`.

### `parseAndRunWorkflow` -- Pre-Built Workflows

A standalone utility for executing a workflow document that already exists (loaded from a file, database, or API response).

```typescript
function parseAndRunWorkflow(opts: {
  json: unknown;
  harness: AgentHarnessContract;
  ctx: Context;
  tools: Tool[];
  input?: string;
  maxDepth?: number;
  layers?: ReadonlyMap<string, ContextLayer>;
  workflows?: ReadonlyMap<string, WorkflowDocument>;
  maxRecursionDepth?: number;
}): Promise<string>
```

`maxRecursionDepth` (default `100`, `Infinity` for none) bounds recursion through the `workflows` registry; see `subflow` → Recursion. `dynamicWorkflow` takes no such option: its planner emits inline subflows only and has no registry to recurse through. The `workflow()` builder (spec 02) takes the same `workflows` + `maxRecursionDepth` pair, and a `workflow({ ref })` step counts its own ref as the first resolution.

This validates the document (schema + depth, throwing `WORKFLOW_VALIDATION_FAILED`), hydrates it, executes it via the harness inside a `workflow.run` trace span, and returns the final output:

```typescript
const result = await parseAndRunWorkflow({
  json: JSON.parse(workflowJson),
  harness,
  ctx,
  tools,
  input: userPrompt,
});
```

## Constraints

### No In-Process Closures

Programmatic `runCode` accepts an `execute` closure, which is not JSON-serialisable. The `runCode` node instead carries its body as a code STRING dispatched through a subprocess adapter — never eval'd in-process. In-process computation is expressed as a `compute` expression (spec 33), which is interpreted as data, or through tool calls and LLM steps.

### Static Lazy Fields Only

All fields in `WorkflowNode` are static JSON values. Fields that accept functions in the native builders (e.g., `fork.paths`, `branch.route`) are replaced with declarative equivalents (static arrays, substring matches, expressions).

### Tool Names Resolved at Hydration Time

Tool references are strings, not `Tool` objects. Resolution happens once during hydration, not at each execution. If the tool registry changes after hydration, the hydrated step tree continues to reference the tools that were resolved at hydration time.

### Maximum Tree Depth

Tree depth is enforced at parse time to prevent unbounded recursion in LLM-generated workflows. The default limit is `5` levels of structural nesting, configurable via the `maxDepth` option on `parseAndRunWorkflow` and `dynamicWorkflow`. Depth does not see through `subflow` refs; recursion through them is bounded at execution time by `maxRecursionDepth` instead (see below).

### Unbounded Control Flow Is Opt-In

Two features let a workflow run without a static bound, and both are explicit opt-ins:

- **Uncapped loops.** `loop.maxIterations: "infinity"` removes the iteration cap; the loop ends only through its `until` predicate, an error, or an aborted context.
- **Recursive subflows.** Named refs may recurse; the path depth is capped by `maxRecursionDepth` (default `100`), which a host may raise to `Infinity`.

A host that runs untrusted documents keeps the defaults it wants enforced: the schema accepts `"infinity"`, so a host that must bound every loop rejects it before hydration, and a host that must bound recursion keeps `maxRecursionDepth` finite.

## Plan-Memory Integration

The plan layer (spec 12, `plan()`) authors plans directly in this format: `PlanState.planTree` is a `WorkflowDocument`, and `PlanState.workflows` is a `Record<string, WorkflowDocument>` of named workflows the tree references via `subflow` nodes. The layer validates documents at authoring time (schema, depth, optional node-kind profile, ref slug syntax) and rejects dangling refs before requesting approval. Recursive refs are legal, matching the runtime; their depth is bounded when the plan executes.

On approval, the host feeds both pieces straight into this runtime:

```typescript
await parseAndRunWorkflow({
  json: state.planTree,
  workflows: new Map(Object.entries(state.workflows)),
  harness, ctx, tools, layers,
});
```

The split keeps the human-reviewed tree small — mechanics factor into named workflows the model authors and revises independently — while the whole plan stays one inspectable, portable JSON structure with stable node ids.

## Error Kinds

The JSON Workflow Runtime introduces the following `NoeticConfigError` codes:

| Code                           | When                                                                     |
|--------------------------------|--------------------------------------------------------------------------|
| `WORKFLOW_VALIDATION_FAILED`   | Document fails schema validation or exceeds `maxDepth` at parse time.    |
| `UNKNOWN_NODE_KIND`            | A node kind has no registered hydrator.                                  |
| `UNKNOWN_TOOL_REFERENCE`       | A tool name in the document is not in the hydration registry.            |
| `UNKNOWN_LAYER_REFERENCE`      | A layer name on a `withContext`/`spawn` node is not in the layer registry.   |
| `UNKNOWN_ACP_AGENT_REFERENCE`  | An `acp-agent` node's adapter is not registered.                         |
| `UNKNOWN_UI_LIBRARY_REFERENCE` | A `callModel` node's `output.library` is not in the codec registry.           |
| `UNKNOWN_SUBPROCESS_REFERENCE` | A `runCode` node's `subprocess` ref cannot be resolved.                      |
| `UNKNOWN_UNTIL_PREDICATE`      | An until predicate kind is unrecognised.                                 |
| `INVALID_UNTIL_DECIDER`        | A decide until predicate does not ask exactly one boolean question (raised at hydration by `loop`/`any`/`all`). |
| `UNKNOWN_WORKFLOW_REFERENCE`   | A `subflow` ref names no registered workflow (raised at execution time). |
| `WORKFLOW_RECURSION_LIMIT`     | A named ref would resolve deeper than `maxRecursionDepth` (raised at execution time). |
| `INVALID_MAX_RECURSION_DEPTH`  | `maxRecursionDepth` is not a positive integer or `Infinity` (raised when a named ref first resolves). |
| `INVALID_FORK_INPUT`           | A dynamic fork's input does not resolve to an array.                     |
| `INVALID_REPLAY_KEY_INPUT`     | A `replayKey.from` node's input is not a JSON object (raised by the key function at dispatch; the interpreter downgrades it to a warning). |
| `EXPRESSION_FAILED`            | A `compute` expression, a route's `when`, or a `when` until predicate fails to evaluate or gives a non-boolean where a boolean is required (raised at execution time; spec 33). |

### Expression Failures

The hydrator prefixes an `EXPRESSION_FAILED` message with the node id. Where it surfaces depends on the node:

| Node                       | Surfaces as                                                                  |
|----------------------------|------------------------------------------------------------------------------|
| `compute`                  | A `step_failed` `NoeticError` from the node, whose `cause` is the `NoeticConfigError` (the node runs as a `runCode` step). |
| `conditional` route `when` | The `NoeticConfigError` itself, thrown from the route function.               |
| `loop` until `when`        | A stop: the loop ends and the message becomes the verdict's reason (spec 05). |

      timeout: z.number().int().positive().optional(),
      layers: z.array(z.string().min(1)).min(1).optional(),
    }),
    z.object({
      kind: z.literal('withContext'),
      id: z.string().min(1),
      child: WorkflowNodeSchema,
      layers: z.array(z.string().min(1)).min(1),
    }),
    z.object({
      kind: z.literal('loop'),
      id: z.string().min(1),
      body: WorkflowNodeSchema,
      until: UntilPredicateSchema,
      maxIterations: z.union([z.number().int().positive(), z.literal('infinity')]).optional(),
    }),
    z.object({
      kind: z.literal('sequence'),
      id: z.string().min(1),
      steps: z.array(WorkflowNodeSchema).min(1),
    }),
    z.object({
      kind: z.literal('schedule'),
      id: z.string().min(1),
      step: WorkflowNodeSchema,
      interval: z.number().int().positive(),
      onError: z.enum(['continue', 'fail']).optional(),
    }),
    z.object({
      kind: z.literal('subflow'),
      id: z.string().min(1),
      document: WorkflowDocumentSchema.optional(),
      ref: z.string().min(1).optional(),
      input: z.string().optional(),
    }).refine((node) => (node.document === undefined) !== (node.ref === undefined), {
      message: "subflow node requires exactly one of 'document' (inline) or 'ref' (named).",

  ])
);

  version: z.literal(1),
  root: WorkflowNodeSchema,
});

## Future Considerations

- **Custom until predicates via registered names.** A plugin could register a named predicate (e.g., `until.custom('myCheck')`) that the hydrator resolves from a predicate registry, similar to tool name resolution. This would allow domain-specific termination logic without extending the schema.
- **URI workflow references.** The `subflow` node resolves named refs from an in-memory registry; a URI form could fetch documents from remote workflow libraries, bounded by the same recursion limit.
- **Streaming hydration.** For very large workflows, hydrate nodes lazily as execution reaches them rather than building the entire `Step` tree upfront. This reduces memory pressure and startup latency.
- **Named context layer resolution for `withContext` nodes.** The current design uses string layer names, but the resolution mechanism is left to the `HydrationContext`. A standardised layer registry (analogous to the tool registry) would make `withContext` nodes portable across different harness configurations.
- **Workflow versioning and migration.** When `version` increments to `2`, a `migrateV1toV2` function would transform old documents automatically. The version field exists to enable this without breaking existing consumers.
